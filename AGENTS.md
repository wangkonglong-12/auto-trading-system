# Codex repository guidance

## Current sources of truth

- Use `pyproject.toml` for the source version.
- Use the current-state section at the top of `README.md` for implemented product and runtime status.
- Use the current section of `docs/architecture-boundaries.md` for architectural boundaries. Date-stamped reports and later historical sections are evidence snapshots, not current status.
- Treat `evidence/`, test caches, coverage files, packaged executables, and generated frontend assets as point-in-time artifacts. Never report them as proof that the current working tree passes.

## Keep discovery scoped

- Read and search only the files needed for the task. Do not require a full repository map, all design documents, or all historical reports for a small change.
- Respect `.gitignore` during normal searches. Do not recursively scan `.codex_tmp/`, `dist/`, `build/`, `node_modules/`, virtual environments, coverage output, caches, or binary Word documents unless the task specifically requires that artifact.
- Prefer `rg` and `rg --files` with a narrow path or glob. Do not use unrestricted scans such as `rg -uu` or a recursive filesystem walk from the repository root by default.
- Keep unrelated work in a separate Codex chat so old tool output and history do not become task context.

## Change and verification discipline

- Preserve the trading safety boundary: live orders, live account changes, scheduler registration, deployment, credentials, and external writes require explicit user approval.
- Make the smallest coherent change. Do not refactor large modules while fixing an unrelated defect.
- After a change, run the smallest relevant test, lint, or type-check first. Expand verification when the change crosses modules, affects safety-critical behavior, or a targeted check exposes broader risk.
- Use `scripts/check.ps1` as the full repository gate before a release, after a cross-cutting change, or when the user explicitly requests full validation. It is not the default loop for a documentation edit or a narrowly scoped fix.
- Never claim a test passed unless it was executed against the current files after the latest relevant modification. Label unrun checks and stale evidence explicitly.
- Frontend source under `frontend/operator-console/` is authoritative. Files under `src/auto_trading_system/apps/local_console/static/` are generated by the frontend build; do not hand-edit generated bundles.

## Documentation maintenance

- When current behavior changes, update the current-state section rather than rewriting historical evidence.
- Keep historical version notes date-stamped and clearly marked as superseded where they conflict with the current source.
- Avoid duplicating detailed plans or architecture text in this file; link to the owning document only when a task needs it.
