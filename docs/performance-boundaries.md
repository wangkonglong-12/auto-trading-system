# 性能与资源边界

## 1. 首期容量模型

首期按约15只股票运行。开发机验收把行情热路径放大为15只标的、每只2,000次、合计30,000次
连续回调，覆盖`MockMarketGateway → 回调复制对象 → BoundedEventIngress`完整同步入口。

固定门槛如下：

| 指标 | 门槛 |
|---|---:|
| 回调数量 | 30,000 |
| 丢失/溢出 | 0 |
| 平均吞吐 | 不低于5,000次/秒 |
| 单次入口P95 | 不高于5,000微秒 |
| 测量区间Python增量峰值内存 | 不高于64 MiB |

这些门槛明显高于15只标的的首期预计流量，同时保留共享CI主机的调度余量。生产队列容量仍由版本化
配置控制；队列达到边界时沿用RT-002/TST-005的失败关闭规则。

## 2. Outbox隔离

性能验收让Outbox Dispatcher停在异步远端等待中，再向决策入口发布Broker关键回调。关键回调必须
在5毫秒内进入预留通道，随后才释放Outbox上传；这证明HTTP补传等待不会占用QMT回调线程，也不会
占用Persistence Writer或普通行情队列的容量。

## 3. 执行方式

```powershell
.\scripts\verify-performance-boundaries.ps1
```

脚本先输出真实测量JSON，再运行性能隔离、决策入口、Mock Market和Outbox四个测试文件。测量值、
固定阈值、事件守恒和测试结论会合并为最终JSON。

## 4. 现场复验

目标QMT机器接入后以相同15只标的规模补充真实XtData回调速率、CPU、工作集、磁盘写入和最长持续
运行数据；现场值进入P0/P3证据，不改变本地基线的通过条件。
