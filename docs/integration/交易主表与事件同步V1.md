## 业务规则

`auto_trade_executions` 是主表，一行表示一只股票的一次买入目标到全部卖出的完整过程。收到候选就建主记录，所以未买入、买入失败也能查询。14:40、14:45、14:50 重复入选归并同一行，后续补单和跨日卖出持续更新原行。

主记录唯一范围是：账户内部别名、策略、REAL/TEST 环境、原选股日期、带市场后缀的股票代码。次日再次入选属于另一笔目标；次日卖出前一天持仓仍属于前一天那笔。页面应显示“代码 + 名称”，名称未知为空。

`auto_trade_execution_events` 是子表，保存每次候选接收、执行进度、提交意图、委托状态、成交、报单失败及撤单失败，不覆盖已接收事件。失败后重试成功时主表更新当前结果，旧失败仍留在子表。

```text
量化优名单 → 本机接收 / 限额与去重 → 原有交易引擎 → QMT
                    ↓                  ↓ 委托 / 成交 / 错误
                 独立本机事件文件队列
                          ↓ 独立同步工作线程
              POST /api/auto-trading/execution-events
                          ↓ 一个 MySQL 事务
              不可变事件子表 + 当前状态主表
```

这条上报链路不下单、不授予交易权限，也不修改量化选股结果。名单三批收齐后停止拉取，上报继续独立运行。每只股票金额与每日数量限制仍由交易设置及原有交易门控制。

## 主表内容与状态

| 字段 | 语义 |
|---|---|
| `execution_id` | 稳定交易编号，由唯一范围计算，跨上传及跨日不变 |
| `node_id`、`account_id`、`strategy_id`、`environment` | 来源节点、账户内部别名、策略与环境；不上传完整证券账号 |
| `selection_date`、`symbol`、`name` | 原选股日、例如 `000001.SZ` 的代码、股票名 |
| `phase`、`source_run_id` | 最早入选时段与量化批次；全部时段仍保留在子表 |
| `target_amount`、`target_quantity` | 本机单股金额上限、执行时冻结的目标股数；未确定股数为空 |
| `stage`、`buy_status`、`sell_status` | 整体阶段、独立买入状态、独立卖出状态 |
| `bought_quantity`、`buy_amount`、`buy_average_price` | 累计唯一买入成交股数、金额、加权均价 |
| `sold_quantity`、`sell_amount`、`sell_average_price` | 累计唯一卖出成交股数、金额、加权均价 |
| `remaining_quantity` | 该笔买入成交减去关联卖出成交，不是账户总持仓 |
| `available_quantity` | 暂为空；当前未导入逐笔可卖量的可信观测，不能把剩余量当作可卖量 |
| `first_buy_at`、`last_buy_at`、`last_sell_at` | 实际成交时间，北京时间；未成交为空 |
| `reason_code` | 当前需关注的原因代码；不保存 SDK 任意错误原文 |
| `version` | 该笔已应用的连续事件序号 |
| `created_at`、`updated_at` | 首次接收的业务事实时间、已接收事实中最晚时间；不是网络接收时间 |

主表还保留服务端生成的 `state_json`、`summary_json`，与上述列同事务更新。它们用于重放归约及一致的查询响应，客户端不能提交汇总值覆盖主表。

整体阶段：`WAITING` 等待、`BUYING` 买入中、`NOT_BOUGHT` 未买入、`HOLDING` 持有、`SELLING` 卖出中、`CLOSED` 全部卖出、`REVIEW` 待核验。

买卖状态：`WAITING`/`NOT_STARTED`、`ORDERING`、`PARTIAL`、`FILLED`、`FAILED`、`CANCELLED`、`SKIPPED`、`UNKNOWN`。其中等待和跳过主要用于买入，未开始用于卖出。部分成交后失败仍保留成交数量，不把已经买到的持仓标成零。SDK 接受请求不等于成交；委托报成交但缺少成交明细时为 `UNKNOWN`。不确定结果不自动重下订单。

金额单位元、数量单位股，金额用两位小数字符串，价格用普通十进制字符串，禁止 JSON 浮点数与科学计数法。成交金额逐笔按价格乘股数、四舍五入到分，加权均价保留八位小数。金额尚不包含未核实费用，不代表结算利润。

## 唯一写接口

`POST /api/auto-trading/execution-events`，只允许 HTTPS，无 URL 参数，UTF-8 JSON，最大 65536 字节，每批 1–20 条事件。请求头为 `Authorization: Bearer <交易上报专用令牌>` 和 `Content-Type: application/json`。

请求的全部字段与联合事件结构以 [批次 JSON Schema](../../contracts/executions/v1.batch.schema.json) 为准。最外层只有：

| 字段 | 类型与规则 |
|---|---|
| `schema_version` | 整数 `1`，布尔值不接受 |
| `node_id` | 本机节点标识 |
| `account_id` | 本机配置的内部账户别名，不是证券账号 |
| `strategy_id` | 例如 `TAIL_CLOSE` |
| `environment` | `REAL` 或 `TEST` |
| `events` | 1–20 条事件数组，同一上传范围 |

每条事件必须包含 `identity`、`source_key`、`occurred_at`、`seq`、`fact`，不能添加未定义字段：

- `identity` 包含账户别名、策略、环境、原选股日期 `selection_date` 与股票代码 `symbol`。此处的账户信息由本机主动上报；量化选股 GET 接口仍不需要账户参数。
- `source_key` 是 `sha256:` 加 64 位小写十六进制的源事实去重键。同一源事实重复观测必须保持同键同内容。
- `occurred_at` 必须有 `+08:00` 时区。成交保留 QMT 实际成交时间；候选、进度及提交保留本机观察时间。不得早于选股日，候选必须在原选股日收到；后台拒绝超过自身时间 30 秒的未来事件。
- `seq` 从 1 开始，在一条主记录内连续递增。不同股票各自计数；可在同批上传多只股票，后台按主记录编号排序加锁，并在每笔内按序应用。
- `fact.kind` 决定载荷结构，不能直接把 QMT 原始对象传过来。

| `fact.kind` | 内容 |
|---|---|
| `CANDIDATE` | 入选时段、量化来源批次、名称和本机金额上限 |
| `PROGRESS` | 关联计划摘要、执行状态及目标股数；包含额度/窗口等未买入原因 |
| `SUBMISSION` | 本机订单编号、买卖方向、NEW/CANCEL、数量价格、提交阶段、持仓批次及原订单关联 |
| `ORDER` | 券商委托编号、数量、累计成交量、委托状态及原因代码 |
| `TRADE` | 券商成交编号、本机与券商订单编号、方向、数量、价格、金额 |
| `REQUEST_ERROR` | 可明确关联本机提交的报单错误，保留方向、操作及规范原因代码 |
| `CANCEL_ERROR` | 原本机订单、券商委托编号、方向和规范撤单错误代码 |

QMT 错误只有能唯一关联本机请求序号或订单标记时才能归到某笔。身份不明或关联冲突仍触发原有暂停核验，不猜测归属、不伪造某股票失败。手工订单、启用前缺少持仓关联的旧订单不会被自动接管。

成功为 HTTP 200，正文结构见 [回执 Schema](../../contracts/executions/v1.receipt.schema.json)：

```json
{
  "schema_version": 1,
  "acknowledgments": [
    {"event_id": "<execution_id>:<seq>", "event_hash": "sha256:<64位摘要>"}
  ]
}
```

以上为字段说明，尖括号是占位符，不是可提交数据。后台必须提交事务成功以后才回成功；回执必须完整包含本批每个事件且摘要一致，顺序可不同。本机核对完整回执并持久化确认后，才从待传队列移除。

`execution_id` 为 `exec-` 加 `identity` 规范 JSON 的 SHA-256；`event_id` 为该编号加冒号及十进制序号。摘要规范：把模型序列化为 JSON，键排序、无多余空格、保留 Unicode 字符、UTF-8、禁止非有限数，再取 SHA-256 并加 `sha256:`。共享 Python 模型和归约器在两个项目保持逐字一致；JSON Schema 之外的金额乘法、唯一范围、事件连续性及持仓守恒也必须校验。

### 错误与重传

错误正文统一为 `{"schema_version":1,"error":{"code":"...","retryable":false}}`。

| HTTP / code | 本机行为 |
|---|---|
| 400 `HTTPS_REQUIRED` / `INVALID_REQUEST` | 保留队列、暂停上报，修正配置或数据 |
| 401 `UNAUTHORIZED` | 保留队列、检查专用凭据 |
| 403 `UPLOAD_SCOPE_MISMATCH` | 保留队列、检查节点/账户/策略/环境 |
| 409 `EVENT_SEQUENCE_GAP` | 保留原编号重传；后台缺前序时不接受后序 |
| 409 其他冲突 | 保留队列、人工核验；相同事件编号内容不同不能覆盖 |
| 429 / 500 / 502 / 503 / 504 | 保留队列、指数退避，最长 60 秒；采纳 1–60 秒 `Retry-After` |
| 503 `REPORTING_DISABLED` | 后台未启用；本机仍保留队列并退避 |
| 超时、断网、成功回执丢失 | 原事件原编号重传，不触发任何买卖重试 |
| 200 但回执不全、重复或摘要不同 | 不确认，暂停上报并待核验 |

相同事件编号且摘要相同：返回原确认，不重复插入或累计成交。相同编号内容不同、同一源键换序号、交易归属冲突或违反成交守恒：整批回滚，无部分成功。主表使用行锁，子表有事件编号、主记录+序号、主记录+源键唯一约束；同批主表与子表同事务提交。

后台每进程最多 2 项此接口数据库工作、4 次/秒请求；读取正文 2 秒、等待数据库工作 8 秒。等待超时不释放仍在运行的工作额度，所以客户端必须能接受“后台已提交但回执没收到”的重传。

## 后台查询接口（供后续页面）

以下`/executions`列表和明细是管理员网页接口，继续沿用后台管理员登录。2026-10-26新增本机历史读取入口`GET /api/auto-trading/execution-history`，使用系统设置中已有统一integration_token，必填account_id、strategy_id，环境仅REAL，复用下述筛选、分页及Excel导出。旧独立上传令牌不能调用此入口；统一令牌也不能代替管理员JWT访问网页管理接口。

- `GET /api/auto-trading/executions`：可组合 `symbol`（六位代码或带.SH/.SZ）、`buy_from`/`buy_to`、`sell_from`/`sell_to`、`account_id`、`strategy_id`。买入按 `first_buy_at`、卖出按 `last_sell_at`，北京时间起止日均包含；空成交时间不匹配对应日期条件。开始晚于结束返回422。默认REAL，可显式TEST；旧 `trade_date` 仍可按原选股日筛选，但已非必填。
- 分页 `offset=0&limit=50`（limit 1–100，offset 0–100000），返回 `{"items":[...],"has_more":false}`。`export=true` 忽略分页，从同一查询条件导出真正的.xlsx，最多10000条，超过返回422 `EXPORT_TOO_LARGE`，不会截断成功。代码和名称均按文本单元格写入，避免丢前导零或执行公式。
- `GET /api/auto-trading/executions/<execution_id>?after_seq=0`：返回 `{"execution":{...},"events":[...]}`；每页最多100条事件，不存在时execution=null、events=[]。

本机历史页经操作员会话校验后，由本机从Windows凭据库读取统一接口令牌，固定当前配置账户、策略、REAL，不接受浏览器覆盖范围。查询和导出仅执行GET，不创建后台登录会话，不向浏览器返回令牌。缺少或拒绝令牌提示核对系统设置，不要求输入管理员账号密码，也不当成本机会话失效。沿用既有显式HTTP/HTTPS后台配置；HTTPS保持证书校验，不用SSH桥代替业务请求。此入口只读取历史，统一令牌本身仍有此前已授权的其他接口权限，本次未改变上传授权。

以上筛选与导出后台已授权发布，20项实际服务检查通过；本机页面尚未发布，直连仍需有效HTTPS入口。详见[发布验收](历史交易筛选导出发布验收_20261023.md)。主记录响应字段见 [主记录 Schema](../../contracts/executions/v1.summary.schema.json)。跨日卖出继续更新原主记录，尚不提供“所有未平仓”专用接口。

## 配置与启用边界

后台新增配置：

- `AUTO_TRADE_EXECUTION_REPORTING_ENABLED`，默认 `false`。
- `AUTO_TRADE_EXECUTION_UPLOAD_GRANTS`，默认空 JSON 数组。每项必须有 `node_id`、`account_id`、`strategy_id`、`environment`、`token`；最多 16 项。同一账户+策略+环境只允许一个写入节点。

上报令牌须独立随机生成，为 43–256 位 base64url 字符，不能复用名单只读令牌或其他节点令牌；范围必须与本机完全一致。不要把令牌写进仓库、页面或日志。本轮没有创建或修改这些真实配置。

本机仅在节点配置增加 `execution_reporting` 时创建记录器和上传任务；例如以下只是配置片段：

```json
{
  "execution_reporting": {
    "token": {
      "source": "WINDOWS_CREDENTIAL_MANAGER",
      "target": "AutoTrading/node-main/execution-upload",
      "encoding": "utf-16-le"
    }
  }
}
```

值是凭据引用，实际秘密另存 Windows 凭据管理器，不能在 JSON 中填写密码。引用及解析结果都须与名单、量化签名和各 IPC 密钥分离。`QMT_READ_ONLY` 不能启用策略交易上报；`MOCK` 只上传 TEST，`QMT_TRADING` 对应 REAL。上报配置不解除任何交易授权或恢复限制。

显式迁移文件位于量化项目 `backend/scripts/auto_trading/migrations/20261023_execution_reporting_v1.sql`，只创建这两个专属表，不在启动时建表。本次已授权执行并核对正式结构、索引及外键；上传启用前仍须建立独立范围凭据、修复有效 HTTPS，再进行独立 TEST 接入验收及获准的真实路径验收。

## 本机持久化与恢复

引擎将观察到的事实交给单一文件线程，写入受保护数据目录的 `jobs/.execution-reporting.json`，文件刷新后原子替换；上传使用独立网络线程，不阻塞选股拉取，也不打开关键交易 SQLite。队列最多 10000 条待传事件、10000 个主记录，总文件最大 32 MiB；单笔最多 2048 个提交及 10000 个唯一成交。

文件保存连续序号、去重键、待传事件、订单与持仓批次关联；已确认后仍保留序号和去重依据。包含在现有节点备份恢复范围中。写入失败、容量耗尽或归属不明会暂停并阻止新增提交，保留文件等待维护；上传暂时断网则排队重试。身份、部署代际或恢复范围改变时不自动套用旧队列。

卖出通过本机已持久化的持仓批次关联原买入。同一卖单可以归属同一主记录的多个批次；跨多个独立主记录的卖单必须拆开，当前不做猜测分摊。现有实盘单批次卖出约束保持原样，未新增卖出策略。

已落盘事件可跨进程重启重传。突然断电可能先于异步文件写入，恢复依靠原交易 Journal、持仓批次及 QMT 查询补齐可证实事实；无法重建的瞬时过程或错误不能承诺恢复，保持未知并核验。不得声称断电前每条瞬时状态都绝对不会丢失。
