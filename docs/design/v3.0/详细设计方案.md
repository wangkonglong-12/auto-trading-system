# 尾盘量化自动交易系统总体与详细设计方案

版本 V3.0　编制日期 2026年9月6日

面向项目负责人、量化研究、交易系统开发、测试与运维人员

## 1 设计结论与业务目标

系统采用“量化研究服务、独立交易管理中心、Windows交易执行节点”三层架构。量化研究服务发布正式选股结果；交易管理中心生成计划、保存中央交易账本、提供监控与治理；Windows节点持有唯一QMT交易会话，完成行情驱动决策、订单管理、账户风控和故障恢复。管理中心与Windows节点属于自动交易产品，分别构建和发布。

首期服务一个专用普通A股账户，运行尾盘买入与下一交易日退出策略，同时交易股票上限15只。资金规模目标覆盖约10万元至500万元。扩容依据为市场容量、实际成交质量和运维能力；账户金额本身不要求把交易内核改成分布式系统。

本方案的质量目标是每笔委托可追踪、每次状态不确定有处理路径、每项控制有生效回执、每次恢复有证据。策略盈利能力使用独立的研究和实盘评估流程；系统验收证明执行正确性和故障处置能力。

### 核心架构决定

| 设计事项 | 本方案采用 | 选择理由 |
| --- | --- | --- |
| 项目与部署 | 独立自动交易项目，中央服务与Windows节点分别发布 | 把选股系统与真实交易的依赖、发布及故障影响分开 |
| Windows结构 | 交易核心、节点代理、Tick归档、监护四个进程 | 网络重试、页面查询和压缩归档具有独立资源与重启边界 |
| 交易核心 | Python 3.12 x64，单一决策循环，QMT请求线程与存储线程 | 状态所有权清晰，SDK和磁盘等待从决策循环移出 |
| 本地恢复存储 | APSW绑定的SQLite/WAL，唯一数据库连接所有者 | 小规模账户使用本地事务和唯一约束直接实现恢复与去重 |
| Tick保存 | 独立归档进程写Parquet/ZSTD | 保存收到的原始行情及质量信息，盘中决策消费内存数据 |
| 中央存储 | 独立MySQL 8.4实例和独立数据库账户 | 交易事件、投影和报表的负载具备独立资源边界 |
| 跨机交互 | Windows主动HTTPS拉取与回传，持久化后逐条确认 | 支持断网补传和可解释的控制延迟 |
| 计划可信性 | 正式选股快照、不可变计划、Ed25519签名、节点最终准入 | 计划来源、参数版本和实际执行权限分别核验 |
| 发布顺序 | 可运行模拟闭环、真实只读、Shadow、辅助实盘、受限自动实盘 | 每阶段交付可运行成果和可重复验收证据 |

### 业务成功标准

D0正式结果发布后，节点在允许时间窗内按已冻结预算买入。D1为交易日历中的下一交易日，节点按持仓绑定的退出策略管理可卖数量。停牌、跌停无对手盘及券商故障会产生延期退出任务，由系统持续跟踪到真实持仓归零或人工接管完成。

一笔业务链必须贯通 source_run_id、plan_id、allocation_id、intent_id、client_order_id、券商委托和成交。每天能回答实际买了什么、用了哪个规则、为什么没有买满、为何卖出、未处理风险在哪里、成交费用与账单是否已核实。

### 指标口径

本文所有延迟、容量、资源和工期数值均为设计目标或工程初值。它们需要在目标机器与实际券商环境测量后形成发布基线。已有单元测试数量和微基准结果不代表新版进程结构、实盘链路或收益已通过验收。

## 2 需求基线与重新设计重点

### 业务范围

首期包含沪深主板、创业板及已开通权限的科创板普通股票；标的进入计划前验证账户交易资格。三个市场分组的选股配额属于Selection Policy，执行节点只消费正式分组与排名。其他品种通过独立交易规则包扩展。

策略由五个明确接口组成：Selection决定标的；Allocation决定组合预算；Entry决定入场条件；Exit决定持仓减仓目标；Execution决定拆单与报价。账户风控对所有策略统一生效。首期账户内同一股票由一个活动策略持仓批次管理；后续多策略共持通过显式的虚拟持仓分配扩展。

### 时间定义

14:31、14:34或14:40只能表示某个选股流程的调度或预期完成时间。系统以正式结果中的 completed_at、published_at 和数据截止时间决定可用性。计划接收后计算实际入场时刻为 entry_not_before 与节点准备完成时间中的较晚者，并验证剩余执行时间。

本版默认入场允许窗口为14:35:00至14:55:30；正常阶段结束于14:52:00，最后90秒留给撤单与确认。剩余窗口不足120秒时生成当日放弃入场的结果。14:56:30仍有未确认活动单时，节点进入撤单异常处置，14:57后的状态以交易规则与券商事实处理。此处时间均为Asia/Shanghai。交易所时段依据见[S05][S06]。

### 本版解决的问题

| 问题 | 重新设计的处理 | 可验收结果 |
| --- | --- | --- |
| 页面、同步、归档与交易共进程 | 按故障来源拆为独立进程，资源预算与IPC限额固定 | 杀掉代理或归档进程，核心仍能管理已有订单 |
| 交易后台增量影响量化服务 | 中央交易管理独立部署，量化服务提供正式结果读取契约 | 交易中心故障不占用选股数据库写事务 |
| 数据库被描述为普通日志 | 明确为订单提交与恢复事务存储 | 没有持久化成功证据的意图无法进入报单调用 |
| 计划时间与真实产出漂移 | 按发布时间准入，截止时间与最小执行时长同时检查 | 迟到结果得到确定的执行或放弃结论 |
| 订单状态按简单顺序覆盖 | 累计成交、券商状态、撤单请求和未知标记分别保存 | 撤单与晚到成交交错仍能算出正确剩余量 |
| 次日收益与当日涨幅混用 | gap、市场涨幅、持仓收益分别命名 | 同一输入能够重放得到一致卖出原因 |
| 阶段完成依赖模块数量 | 使用纵向业务链验收与独立的交付状态 | “已编码”“模拟通过”“现场通过”“可发布”分别可查 |

## 3 系统边界与部署架构

### 三层职责

量化研究服务保留选股、评分、行情研究和正式运行记录。它提供按运行ID读取的不可变结果快照，并授予交易管理中心只读服务身份。交易管理中心把快照转成账户计划，管理策略包、授权、计划签名、事件接收、投影、对账、报表和告警。Windows节点向管理中心主动获取数据并回传事实。

在用户访问上，量化门户可以提供自动交易入口，跳转到独立交易管理页面。反向代理可把同域名下的 /trading/ 分配给新服务。页面入口统一不意味着后端进程、权限或数据库共用。

### 部署单元

| 单元 | 进程与数据 | 首期资源预算 | 失效影响 |
| --- | --- | --- | --- |
| 量化研究服务 | 原服务与选股数据库 | 按现有容量规划 | 当日新计划来源暂不可用 |
| 交易管理中心 | API、单Worker、独立MySQL实例、管理页面 | 独立Linux虚拟机4核8GB，SSD100GB起 | 计划发布、远程控制、中央查询与同步暂不可用 |
| Windows执行节点 | QMT、四个产品进程、本地事务库与Tick盘 | 8核16GB，系统与交易数据SSD，建议独立归档物理盘 | 现场执行与行情采集受影响 |
| 备份目的地 | 加密事务库备份、中央备份、证据归档 | 独立故障域，容量按留存计算 | 备份延迟触发告警，恢复能力下降 |

资源数值是初始预算，包含持续监控和故障恢复余量。归档与Journal处于不同物理盘时可进一步减小磁盘竞争；仅划分目录或分区不会产生物理I/O隔离。中央服务增加一台虚拟机和一套数据库实例，是取得量化服务独立资源边界的明确运维成本。

### 事实归属

| 数据 | 权威来源 | 派生状态 |
| --- | --- | --- |
| 正式选股与数据完整性 | 量化服务不可变运行快照 | 计划生成资格 |
| 计划、策略包与风险配置版本 | 交易管理中心签名发布物 | Windows已验签副本 |
| 委托、成交、现金和真实持仓 | 券商交易系统经QMT查询与回报 | 节点运行视图及中央历史投影 |
| 本地提交动作与交易控制 | Windows事务Journal | 中央审计镜像 |
| 正式交割费用与资金流水 | 券商正式账单 | 会计凭证、净收益与净值报表 |
| 展示状态 | 带时间与版本的只读投影 | 页面缓存，显示新鲜度 |

QMT四类查询的返回时点可能不同，组合快照称为观测窗口。中心接收时间不能替代券商事实时间，最后一次请求成功也不能证明所有数据同时一致。

## 4 技术路线与工程边界

### 确定技术栈

| 领域 | 采用技术 | 版本和交付要求 |
| --- | --- | --- |
| Python运行时 | CPython 3.12 x64 | Windows与中央分别固定补丁包、SHA256和依赖锁；QMT三元组先验收 |
| 交易核心 | asyncio、不可变领域事件、显式状态归约 | 核心模块仅依赖领域端口；SDK和数据库通过适配器访问 |
| QMT适配 | 券商确认的XtQuant包，XtQuantTrader与xtdata | 固定券商客户端、SDK、Python组合及接口能力报告 |
| 本地事务 | APSW、SQLite/WAL | SQLite至少3.51.3并使用已验收补丁版本；锁文件精确到包hash |
| 跨进程通道 | Windows Named Pipe、pywin32、UTF8 JSON帧 | 显式DACL、版本、消息长度、角色授权、关联ID与有界队列 |
| 节点代理与中央API | FastAPI、Pydantic 2、HTTPX、Uvicorn | API契约由Schema和OpenAPI共同发布 |
| 中央持久化 | MySQL 8.4 InnoDB、SQLAlchemy 2、PyMySQL、Alembic | 独立实例；迁移与应用版本对应；写入成功后回执 |
| 中央作业 | APScheduler 3.11单Worker与数据库作业记录 | 补跑和幂等由持久化作业键保障 |
| 前端 | Vue 3、TypeScript、Vite、Naive UI、ECharts | 本地台和中央台独立应用；共享无业务权限的UI基础组件 |
| 行情归档 | PyArrow、Parquet、ZSTD | 分钟分片、列式Schema与文件完整性manifest |
| 签名与凭证 | cryptography Ed25519、HMAC SHA256、Windows凭证保护 | 计划签名私钥与节点HTTP密钥独立管理 |
| 测试与质量 | pytest、Hypothesis、Ruff、mypy、Vitest、Playwright | 领域性质测试、真实数据库测试、回放和故障注入共同验收 |

Python3.12是当前设计目标，实际券商SDK仍需在该解释器上验收。官方已提供支持Python3.12及3.13的SDK版本说明，但券商交付版本可能滞后[S02]。若目标环境不支持3.12，形成一项版本例外记录后重新发布兼容清单；其他组件的验收条件保持一致。

APSW作为SQLite绑定允许单独锁定其内置SQLite版本，避免Python解释器升级与数据库补丁升级被绑定。官方说明其PyPI包内嵌私有SQLite副本[S04]。生产安装只使用已构建并校验的离线wheel，目标机现场安装不承担编译任务。

### 代码组织

自动交易项目采用单仓库多发布包，目录为 packages/domain、packages/contracts、services/control_plane、services/windows_node、apps/central_console、apps/local_console、tests、deploy、docs。windows_node内部按engine、broker、market、journal、agent、recorder、supervisor拆分。依赖图由检查工具约束。

domain包含值对象、策略状态、订单模型和纯计算规则；contracts包含协议模型和测试向量。SDK、HTTP、SQL、文件系统与系统时钟均通过端口接入。领域逻辑可在模拟、回放和实盘共用。中央与节点分别构建wheel与锁定依赖，前端分别构建静态资源。

### 主要取舍

Python适合当前频率、SDK生态与团队维护。对延迟的投入集中在排队、持久化、行情新鲜度和券商响应，避免把微秒级纯函数基准当成实际成交速度。中央异步作业采用数据库记录加单Worker，首期无需管理独立消息集群。未来多账户以账户分区增加节点与中央投影Worker，沿用相同领域协议。

## 5 Windows进程与并发详细设计

### 四个进程

| 进程 | 主要职责 | 拥有的资源 | 重启策略 |
| --- | --- | --- | --- |
| trading engine | 行情规范化、决策、风控、订单、QMT会话、对账、本地事务 | 唯一账户Mutex，唯一Trader，Journal连接 | 启动恢复后进入READY_PAUSED |
| node agent | HTTPS同步、控制转交、本地页面、诊断查询、文件上传 | 网络连接、页面缓存、HTTP凭证 | 独立重启，向核心恢复读取游标 |
| tick recorder | 完整收到的Tick、归档manifest、压缩与保留作业 | 归档目录与独立接收队列 | 独立重启并登记采集缺口 |
| supervisor | 生命周期、进程句柄、心跳、故障标记、最低限度本地停机入口 | 子进程句柄、安装清单、受保护控制管道 | Task Scheduler负责拉起监护本身 |

engine内有决策循环、SDK请求执行线程、Journal Owner线程以及QMT自带回调线程。所有运行态由决策循环修改；Journal Owner独占数据库连接和所有读写、Checkpoint、备份动作。其结果以不可变消息回到循环。代理获取历史事件时发有界查询任务，最多每页200条，由Owner在短读事务中返回。

节点代理把界面和网络操作转换为控制请求，engine校验作用域、签名、有效期和状态版本后决定是否执行。Tick recorder只接收行情副本。它的崩溃不会取消Trader，也不会阻止Journal提交。

### 事件调度

交易回调通道保存委托、成交、错误及账户变化；普通行情通道保存逐条价格路径；控制通道保存急停与健康锁。循环每轮优先处理控制及交易事件，再按每标的配额公平处理行情。单个回调只复制基本字段、附接收时间并非阻塞入队，复杂校验与策略计算在循环执行。

峰值回撤策略依赖价格路径，因此正常运行保留按接收顺序的行情事件。行情积压达到边界后冻结受影响标的入场，记录缺口并恢复状态；仅靠“保留最新一条”无法证明中间峰值未丢失。归档副本队列单独计数，其丢包不会修改策略所见行情序列。

| 通道 | 首期容量初值 | 达到边界的行为 |
| --- | --- | --- |
| 控制与健康 | 独立急停锁存位加1024条控制消息 | 急停锁存先同步改变报单许可；详细审计排队落盘 |
| 委托与成交 | 8192条 | 溢出设置交易事实缺口锁，停止新的报单并主动对账 |
| 策略行情 | 32768条且内存上限64MiB | 超限冻结相关策略，记录缺口，重新建立指标基线 |
| 归档副本 | 65536条且内存上限128MiB | 丢弃超出部分并记录起止序号与数量 |
| 待持久化事务 | 2048个任务，优先意图与交易事实 | 高水位暂停新入场，保留事实与控制处理预算 |

容量在目标机压力测试后冻结。调度处理每批最多100条或消耗2ms即让出控制权。每个SDK查询同一时刻最多一个，在途查询超时后进入隔离状态；计时器取消Future不等于底层SDK调用已经终止。

### IPC协议

管道分为control、state、events、ticks四类，使用独立队列和限额。帧采用4字节大端长度加UTF8 JSON，control上限64KiB，events上限1MiB，超过上限在解析前拒绝。消息携带 protocol_major、request_id、engine_boot_id、sender_role、deadline、payload。状态响应附state_version和as_of，控制必须带expected_state_version。

管道ACL仅授予专用Windows用户与必要的SYSTEM访问权，并拒绝远程客户端。服务端还检查调用角色与动作权限。Windows默认命名管道安全描述符可能授权更宽的读取范围，因此安装时必须显式设置DACL[S09]。序列化采用数据Schema；所有控制按request_id幂等，连接中断后的重试不会复制业务动作。

### SDK卡死的边界

SDK线程隔离能避免正常阻塞I/O占用决策循环，但原生扩展崩溃或长时间占有GIL仍可能影响整个engine。supervisor通过独立进程发现心跳停滞，先锁存HALT，随后按故障预案等待或终止该engine进程。重新启动必须确认旧进程已退出、Mutex已释放并完成券商对账；单纯等待租约到期不能证明旧进程停止报单。

## 6 调度与每日业务流程

### 调度职责

Windows Task Scheduler在专用用户登录时启动supervisor，并每分钟检查其存活。supervisor按依赖顺序启动engine、agent和recorder。业务调度由长期运行的进程承担：agent定时调用交易管理中心，engine调度QMT查询、策略时间事件与本地维护。

因此，计划拉取、交易结果回传与盘后账单上传都是Windows主动定时调用接口。Windows任务计划程序提供进程生命周期保障，agent内部计时器负责每秒级业务同步，engine保持唯一QMT会话。

### 每日时序

| 时间或事件 | 执行动作 | 完成证据 |
| --- | --- | --- |
| 08:45至09:10 | 登录环境确认、日历与规则包、连接、Journal检查、账户初始对账 | readiness报告及运行模式READY_PAUSED |
| 09:30起 | 已授权的D1持仓退出；按策略维护价格路径与可卖数 | 退出状态、订单和持仓事件 |
| 14:20 | 检查选股来源、计划轮询、行情与资金预算 | D0入场准备报告 |
| 正式结果发布 | 中央读取不可变快照并签发计划；agent拉取，engine校验并持久化 | 源hash、计划hash、LOADED回执 |
| 14:35至14:52 | 满足条件的账户计划正常拆单执行 | 已成交、活动单与剩余预算 |
| 14:52至14:55:30 | 缩短等待并按剩余容量完成；价格上限保持有效 | 每次追价和放弃原因 |
| 14:55:30 | 截止新增普通入场，发起剩余活动买单撤单 | 各订单撤单结果 |
| 14:56:30 | 汇总待撤、未知与预计进入收盘阶段的订单 | 异常告警和人工处置清单 |
| 15:10起 | 订单、成交、资产、持仓观测窗口与对账 | provisional对账报告 |
| 15:30起 | 按健康条件做维护、备份、归档；待取得正式账单后复核 | 备份hash、归档manifest、settled账本 |

固定时间作业用 trade_date、job_type、account_id 唯一键登记开始与完成。进程恢复后扫描未完成作业，根据有效期补跑；过期入场作业登记SKIPPED。耗时与退避使用单调时钟，交易日期和业务窗口使用上海时区及交易日历。时钟倒退不会触发同一规则第二次执行。

### 网络同步频率

agent在14:20至14:55:30每2秒拉取计划，其他时段每30秒同步计划状态；每2秒拉取控制命令；每1秒或50条上传交易事件；每5秒上传心跳。HTTP连接超时3秒，普通请求总超时8秒，事件上传15秒。重试采用1、2、4、8、16、30秒退避上限并增加随机抖动，重试流量与控制轮询使用独立并发配额。

## 7 量化服务与交易管理中心交互

### 正式结果读取契约

量化服务提供 GET /api/v1/selection-runs/final 与 GET /api/v1/selection-runs/{run_id}?revision={revision}。前者按strategy_id、trade_date和delivery_seq查询最新正式发布结果，后者必须指定revision读取固定版本。交易管理中心使用只读服务凭证，2秒轮询正式尾盘发布状态；请求负载上限512KiB、每账户来源共享一次抓取结果。

发布对象称为SelectionSnapshot。run_status=SUCCEEDED、data_completeness=FULL、publication_status=FINAL、finalized=true同时成立才具备真实计划发布资格。正式运行无股票时返回空items和NO_SELECTION原因。运行失败、仍计算或只取得部分市场结果具有独立状态。

| 字段 | 类型 | 定义 |
| --- | --- | --- |
| source_run_id和source_revision | 字符串与正整数 | 正式运行及其不可变版本 |
| strategy_id和algorithm_version | 字符串 | 选股策略与算法版本 |
| trade_date和timezone | 日期与时区 | 结果所属交易日 |
| scheduled_at和completed_at | 带时区时间 | 调度时间与运行结束时间 |
| market_data_cutoff和published_at | 带时区时间 | 数据截止与正式发布时刻 |
| data_completeness与market_coverage | 枚举与列表 | 全量状态和各市场覆盖情况 |
| items | 有序对象列表 | symbol、market、rank、score、reference_price及来源信息 |
| source_hash和delivery_seq | SHA256与单调整数 | 内容指纹与正式交付顺序 |

发布端通过一致性读或已落盘的不可变结果对象生成响应，避免运行头与股票明细来自不同提交。source_hash覆盖结果内容和版本字段。校正结果通过新revision发布；历史revision仍可读取。接口读取失败不会改变选股运行结果。

中心计划的source.completeness明确映射SelectionSnapshot.data_completeness，值保持FULL或PARTIAL。所有来源映射由同一个适配器完成，并使用契约样例验证，避免同名字段在不同服务中出现隐含语义。

读取凭证采用专用服务HMAC密钥，只授予selection:read作用域，并与节点交易接口密钥分开。响应携带source_hash、ETag和响应签名。单次读取使用3秒连接与8秒总超时，单并发；来源拥塞时退避重试，由管理中心记录发布延迟。此接口有独立的限流与查询超时，保护原选股服务的资源。

### 计划发布事务

管理中心校验快照后读取账户授权、策略版本和预算配置，生成PlanEnvelope。在一个本地MySQL事务中保存源快照、不可变计划正文、签名记录和发布事件。唯一键使用 account_id、strategy_id、trade_date、source_run_id、source_revision、allocation_revision，重复作业返回已有计划。

发布事务只访问交易中心数据库。生成失败登记PUBLISH_FAILED及原因，由独立Worker重试。结果读取、计划生成和实际执行的状态分别展示，方便区分“还未选好”“计划发布失败”和“节点未执行”。

### 结果向量化研究的反馈

交易中心提供 GET /api/v2/research/executions 与 GET /api/v2/research/daily-reports，量化研究服务按游标读取已对账交易事实、策略归因和执行质量。响应附账本版本、费用状态和数据截止时间。执行结果的长期查询由交易中心承载；研究服务保存其研究所需的派生特征和报告引用。

## 8 交易计划与版本协议

### 计划内容

PlanEnvelope由不可变payload与签名envelope组成。payload包含schema_major、plan_id、account_id、strategy_id、trade_date、source、execution_window、allocations、policy_bundle、risk_budget、offline_authorization、rulebook_version和target_node_generation。plan_hash为规范化payload的SHA256；signature覆盖固定域分隔字符串和payload字节。业务金额与价格使用十进制字符串，数量使用整数股。

正文采用确定性JSON规则：UTF8、字符串NFC、对象键排序、紧凑分隔、显式布尔和null；小数全部作为字符串。数组保留发布顺序并携带rank。提供覆盖Unicode、空列表、负值、时区和边界金额的跨语言测试向量；签名与plan_hash字段放在正文之外避免自引用。

| 字段组 | 必须包含 | 节点校验 |
| --- | --- | --- |
| 身份 | plan_id、account_id、strategy_id、trade_date | 账户、交易日、唯一性与节点授权相符 |
| 来源 | source_run_id、revision、source_hash、completeness | 正式且完整，哈希可追踪 |
| 窗口 | entry_not_before、stop_new_buy_at、cancel_by、min_execution_seconds | 时间严格有序且剩余窗口足够 |
| 分配 | allocation_id、symbol、target_value、max_value、max_qty、priority | 金额、股数、账户预算和证券规则共同约束 |
| 策略 | entry、exit、execution、risk的版本与hash | 本机支持已安装实现，参数Schema通过 |
| 离线授权 | valid_until、entry_enabled、exit_enabled、session_generation | 只授予有效期内及本次运行的能力 |
| 签名 | key_id、algorithm、payload_hash、signature | 预置可信公钥、签名正确且密钥有效 |

账户预算以绝对人民币金额为计划执行主值；中心同时记录用于计算该金额的资产快照与目标权重。执行期间股价变化不会不断抬高预算。节点根据最新现金、已占用金额和硬上限进一步缩小可执行值。扩大预算需发布新分配版本并重新准入。

### 三组生命周期

发布生命周期为DRAFT、PUBLISHED、WITHDRAWN、SUPERSEDED；它只描述中心发布状态。节点生命周期为RECEIVED、VALIDATED、LOADED、ARMED、EXECUTING、ENTRY_CLOSED。持仓生命周期为OPEN、EXIT_PENDING、EXITING、RESIDUAL、CLOSED。三者通过ID关联，计划入场截止不等于对应持仓已退出。

LOADED表示验签成功并已落盘；ARMED表示本次运行获得执行许可；EXECUTING表示已经开始处理订单意图。回执携带plan_hash、engine_boot_id、state_version、有效能力和原因。中心可明确显示“中心已发布，节点已加载，尚未授权执行”。

### 修改与取消

内容修改产生新plan_id并声明supersedes。旧计划撤回通过带command_id的控制命令传递，节点暂停其新入场并处理活动单后回执。中央仅在取得旧计划执行边界和账户对账结果后，签发替代计划的新增预算。已成交持仓继续绑定原Exit Policy，直到受控的策略变更完成。

通信断开时，中心撤回状态显示PENDING_DELIVERY。节点只能执行已持久化且仍在有效期内的离线授权。短离线授权能更快让新买入停下，但会降低网络波动时的可用性。本版采用当日窗口有效的冻结预算授权，允许已ARMED计划在中心离线时继续；远程急停的即时性由本地值守通道补足，中心页面持续显示最后心跳和授权到期时间。

### 请求认证

HTTPS校验证书与主机名，每节点配置独立HMAC密钥。请求头包含 X-Node-Id、X-Key-Id、X-Timestamp、X-Nonce、X-Request-Id、X-Body-SHA256、X-Signature。签名原文依次包含协议域、方法、规范路径、排序编码后的query、节点、密钥ID、时间、nonce、request_id和实际请求体hash，行分隔使用LF。

认证服务先验证签名与时间范围，再原子登记nonce。允许时间偏差30秒，nonce保存10分钟。网络重试保持业务request_id和正文，使用新nonce与新认证时间。重试请求收到之前已提交的同内容结果；相同request_id但正文不同返回409。安全事件不记录secret或完整认证头。

HTTP响应绑定请求ID、状态码、响应体hash与响应时间并签名，包含200、204和304等无正文响应。代理验证传输完整性；engine独立验证计划和能力扩大的控制对象的Ed25519签名。私钥保存在中央受保护凭证系统，节点只保存可信公钥。全新公钥通过已签名的发布包分发；key_id本身不具有建立信任的权限。

### 事件模型与接收事务

事件封套包括event_id、journal_generation、event_seq、boot_id、account_id、event_type、occurred_at、received_at、plan_id、intent_id、client_order_id、broker_key、payload_schema和payload_hash。event_seq在同一Journal代际内跨进程重启递增；新建数据库或从旧备份恢复时更换journal_generation，并登记与旧代际的关系。

一个批次最多200条或512KiB。服务端完成认证后，在MySQL事务中对每条事件做身份、结构、hash和唯一键校验，写原始事件以及投影待处理记录。结构冲突可用savepoint隔离。事务提交成功后返回accepted、duplicates、rejected及receipt_token；存储失败返回503而不确认任何未持久化事件。投影在独立事务中异步执行。

重复判定必须同时匹配event_id和payload_hash。同ID不同内容属于冲突事件，保留两侧hash与告警。服务端返回的连续水位只能表示某代际内从起点连续接收的最大event_seq；收到1、2、4时水位是2。批次HTTP200及最大已见序号均不等于缺口已补齐。

agent携带中心签名接收证明，通过IPC请求Journal Owner标记accepted和duplicates为已送达。ACK落盘前崩溃会导致再次上传，中心幂等返回原结果。rejected原文保留在隔离队列，自动记录协议Incident，人工修复后使用明确的更正事件关联原事件。

### 超时与错误处理

| 响应或异常 | 含义 | 调用方处理 |
| --- | --- | --- |
| 204 | 当前无发布结果 | 按计划继续轮询，维持已有持仓退出任务 |
| 304 | 已验证版本未变化 | 保持已加载版本及原有效期 |
| 400或422 | 结构或业务语义不支持 | 隔离该对象并报告具体字段 |
| 401或403 | 签名、身份或权限失败 | 停止相应同步，锁定新授权获取并告警 |
| 409 | 幂等或版本冲突 | 读取冲突资源并对比，不修改原对象 |
| 429 | 服务限流 | 按Retry-After及重试预算退避 |
| 503或网络超时 | 服务或接收结果不确定 | 相同业务ID重试，Outbox保留 |

### 快照完整性

Snapshot记录query_status、query_started_at、query_completed_at、account_status、order_watermark、各类数据计数与hash。query_status取AVAILABLE、UNAVAILABLE、UNCERTAIN，AVAILABLE可以具有完整空列表。账户、持仓、委托、成交分别报告状态，整组快照只有在完整性检查通过后才可发布complete=true。

大快照按snapshot_id分片，中心在各分片到齐且manifest校验通过后原子发布。查询失败时更新健康信息并保留上一有效视图的原as_of，页面明显显示陈旧。空持仓只有在成功、完整的查询证据下才能覆盖之前持仓。

## 10 本地事务存储与稳定性设计

### SQLite承担的职责

SQLite保存已验签计划、策略版本、订单意图、实际提交尝试、资金及数量预占、券商标识映射、成交去重、控制锁、退出规则状态、原始事件与Outbox。它是恢复交易决策和证明报单动作的事务存储。连续Tick另行归档，常规运行日志另行滚动保存。

任何本地持久化方案都会引入写入延迟和磁盘故障风险。可靠设计把这个成本放在委托提交前，并为超时、提交结果不明、磁盘满和恢复定义行为。故障时牺牲新增交易可用性，保留已经存在的券商事实和人工处置入口。

### 本地存储方案比较

| 方案 | 优点 | 代价 | 本版决策 |
| --- | --- | --- | --- |
| SQLite/WAL | 嵌入式、本地事务、唯一索引、易备份，适合单写 | 写入需串行；维护和版本必须受控 | 采用，Owner单连接和APSW版本锁定 |
| 本机PostgreSQL | 多连接并发与成熟服务器运维能力 | 额外服务、认证、升级、连接失效与资源维护 | 多账户多写需求出现后重评 |
| 追加文件Journal | 顺序写布局可控 | 需要自行实现截断恢复、索引、事务和迁移 | 研究基准候选，首期使用成熟事务引擎 |
| 远程数据库 | 数据集中、集中备份 | 网络成为每笔委托的持久化前置条件 | 用于中央账本与分析 |

对于单账户15只股票，SQLite事务能力和低运维成本适合当前业务，故本版仍选择SQLite。若用户最终指定采用本机PostgreSQL，领域层通过JournalPort替换适配器；该变更需要重做断电恢复、提交不确定性与运维验收，不能把替换组件视为稳定性的自动保证。

### 版本与运行参数

SQLite官方已说明WAL-reset缺陷在特定多连接并发写入或Checkpoint场景中可能造成损坏，并列出3.51.3及后续版本和部分回补版本作为修复版本[S03]。本版要求实际加载库至少3.51.3、固定到验收过的具体补丁及hash；启动报告记录APSW版本、SQLite版本和编译选项。单连接Owner进一步收紧并发结构，版本升级仍为发布前置条件。

| 参数或边界 | 设计值 | 目的 |
| --- | --- | --- |
| journal_mode | WAL | 以标准事务日志支持恢复 |
| synchronous | FULL | 委托前关键事务获得持久化确认[S07] |
| foreign_keys | ON | 保证意图、订单和关联记录一致 |
| busy_timeout | 100ms | 单连接架构下意外竞争快速显露 |
| wal_autocheckpoint | 0 | Checkpoint由Owner按显式作业执行 |
| 事务目标 | P99不超过50ms；应用等待上限250ms | 超时结果进入查证流程 |
| WAL水位 | 64MiB计划维护，256MiB暂停新入场并处置 | 显式维护避免无限增长 |
| 数据盘可用空间 | 至少5GiB且至少10% | 为关键事务与恢复保留余量 |

Owner在无未完成关键写入且没有待提交委托的间隙执行PASSIVE Checkpoint。盘后停止新订单、队列排空后执行完整维护与Backup API。若WAL持续增长而没有合适窗口，则先暂停新入场、完成在途管理，再维护。文件大小、逻辑已Checkpoint页数和实际写入错误分别监控。

### 事务边界

TX1原子保存意图、child order、唯一短令牌、预算预占、ORDER_PREPARED事件与Outbox记录。TX2记录SEND_REQUESTED和派发票据，再把不可变命令交给SDK请求线程。交易回报事务保存原始回报、订单派生状态、成交去重与预占变化、退出状态和Outbox。控制事务保存控制锁、状态版本及审计。

JournalPort提供prepare_order、record_dispatch、apply_broker_event、apply_control、read_recovery、read_outbox、ack_delivery、checkpoint和backup。接口返回commit_id、journal_generation、event_seq及明确结果。领域层通过端口表达业务原子性，SQL语句及文件位置由适配器负责。

### 超时及失败

等待250ms到期仅表示调用方没有及时取得提交结果。intent_id保持原值，进入PERSISTENCE_UNCERTAIN，冻结本次派发并查询该事务是否存在。后续迟到commit回调只补充事实；重新核验当前许可、报价和时窗并产生新的派发票据后才具备发送资格。

数据库不可写时锁存HALT，自动买卖新报单均停止。已发送委托仍可能成交；事件先进入预分配有界内存区，故障包尽力写独立诊断盘，值守人员使用券商终端核实和撤单。副盘也可能失败，因此诊断备用写入不作为继续自动交易的授权。

### 备份与恢复

15:30后使用Backup API生成一致性备份，校验完整性与hash，附上最后event_seq、计划与策略hash，上传独立备份目的地[S08]。本地保留20个交易日恢复备份，中央保留周期见数据保留章节。活动库、WAL和SHM属于关联状态，备份使用数据库API完成。

单磁盘物理损坏时，本地未上传信息可能丢失；本架构不声明此类故障RPO为零。恢复使用异地备份、中心事件副本和券商历史事实重建，仍无法解释的提交保留UNKNOWN并转人工。每个季度演练更换磁盘后的完整恢复。

## 11 订单生命周期与提交正确性

### 标识模型

allocation_id表示一次固定预算分配；intent_id表示某规则的一次业务目标；client_order_id表示一个实际子委托；attempt_id表示该子委托的一次SDK调用记录。每个client_order_id只允许一次进入SEND_REQUESTED。网络或SDK返回不明时，保持原身份查询查证。

intent唯一业务键为账户、策略、持仓批次或计划分配、规则ID、触发阶段、方向。remark_token为本地唯一且固定长度的ASCII令牌，最多24字符；实际回传长度在券商PoC核验。券商委托键按账户、交易日、市场和order_id组合；成交键按券商实测唯一范围使用账户、交易日、市场、traded_id及必要委托字段。

### 提交状态与券商事实分离

本地提交状态为PREPARED、SEND_REQUESTED、DISPATCH_STARTED、OBSERVED、UNCERTAIN。券商状态单独记录原始枚举和最近可信观察；累计成交qty、cancel_requested、remaining_qty、终结原因也是独立字段。

QMT异步请求返回seq用于关联响应，正式委托与成交仍以回报或查询为依据[S01]。订单状态不能简单按整数大小或固定等级覆盖。CANCELLED状态后到达的已发生部分成交仍需入账；成交数量增加必须有成交去重或可信累计查询支持。

### 报单流程

1. 决策循环根据当前行情、账户状态和策略规则生成意图，计算预算与数量。
2. 检查同账户同股票活动单互斥、风险许可、交易时段和报价新鲜度。
3. Owner执行TX1；成功前没有可派发命令。等待失败则进入持久化查证。
4. 决策循环再次校验许可版本、现金预占、行情和截止时间，生成带expiry与permission_epoch的票据；TX2持久化SEND_REQUESTED。
5. SDK线程在调用入口检查票据、当前permission_epoch和单调时钟有效期，原子标记已跨过派发边界后调用order_stock_async。
6. 返回、错误和回调作为事实进入循环。若QMT调用结果不明，标记UNCERTAIN并启动查询恢复。

permission_epoch在急停、风控锁和模式收紧时立即递增。尚未跨过调用边界的旧票据失效；已跨过边界的命令计为在途委托。急停回执必须列出在途集合，不能承诺撤回已经进入券商链路的动作。

### 崩溃窗口

| 崩溃位置 | 恢复时证据 | 动作 |
| --- | --- | --- |
| TX1之前 | 没有意图事务 | 在新运行授权后重新评估规则 |
| TX1后TX2前 | PREPARED且没有SEND_REQUESTED | 释放或重新评估预占，取得新许可再执行 |
| TX2后SDK调用前 | SEND_REQUESTED但未知是否调用 | 作为UNCERTAIN查询券商，恢复不自动重发 |
| SDK实际受理后本地记录前 | 短令牌与提交记录存在，回报可能缺失 | 查询委托及成交映射，绑定原client_order_id |
| 本地成交已提交但中心未确认 | Outbox中存在成交事件 | 相同event_id补传 |
| 中心已接收但本地ACK未落盘 | 中心可给出接收证明 | 重传得到duplicate后提交送达标记 |

券商不提供经过验证的客户端幂等键时，无法通过本地事务证明跨券商的严格exactly-once。本版采用“同一子委托至多一次发送尝试、模糊结果保持未知、券商事实查证”的策略。一次完整查询没有找到订单仍可能来自查询延迟；只有取得明确拒绝/未发送证据，或人工核验形成最终裁定后，才可创建替代子委托。

### 撤单与重报

撤单创建cancel_id并持久化请求，SDK返回只更新撤单请求进度。订单仍保留原数量预占，直到券商终结事实和成交累计量确认。重报数量按意图未完成量、已成交量、其他活动单量和当前可用资源重新计算，且使用新client_order_id。

同一股票账户内最多一个活动方向。由减仓触发与买入残单冲突时，先结束买单并对账，再进入卖出目标。新成交先于委托回报到达时，暂存其关联并查询委托，成交事实始终保留。旧回报无法降低累计已确认成交量。

## 12 账户预算与预占模型

### 资金计算

账户可用于新买入的金额取以下约束的最小值：最新可信券商可用现金减去尚未被该快照反映的本地预占、计划剩余预算、账户仓位余量、单股票上限和流动性允许金额。每笔买入预占限价乘数量加预计费用。预算计算和预占创建由同一决策所有者及事务处理。

券商现金通常已反映部分活动订单冻结。系统维护snapshot_id、observed_order_set和每笔reservation的反映状态。只有尚未体现在同一观测窗口中的预占再从现金扣除，避免重复扣减。观测窗口有交易事件穿越时，重新采集或暂时保留较保守结果。

组合暴露计算同时包含已持仓市值与全部活动买单剩余最大金额。撤单发出后不立即释放预占；明确失败且未形成委托，或券商终态与累计成交查证完成后，按真实剩余部分释放。

### 可卖数量

可卖数量取券商can_use_volume、策略批次剩余量、尚未被券商持仓快照反映的本地卖出预占共同约束。每个持仓批次记录trade_date_acquired、eligible_sell_date、策略归属、已成交卖出和在途卖出。D0买入批次不依靠自然日加一天计算可卖日期。

人工交易、送转、配股、费用修正与历史遗漏均可能改变实际持仓。数量差异锁定受影响股票的自动派发；账户出现无法解释的资金差异时停止新买入。差异处理以券商事实为基础，并保留调整事件和操作者说明。

### 数量和价格规则

InstrumentRule字段包含market、board、instrument_type、min_buy_qty、buy_step、min_sell_qty、sell_step、odd_lot_rule、max_order_qty、price_tick、daily_limits、price_cage、session和effective_date。规则来自可追溯规则包并与券商证券信息交叉核对。

主板、创业板与科创板采用独立规则。例如科创板限价申报最低200股及不足200股余额一次卖出要求，与普通按100股整数手的处理存在差异[S05]。拆单算法调用规则包求出小于或等于预算允许股数的最大合法数量，合法最小数量也无法满足时登记SKIPPED_MIN_ORDER。

### 多策略边界

首期同一symbol同一账户只分配给一个活动策略；中心合并重复候选并给出唯一责任策略。未来允许多策略共持时，新增allocation ledger，由账户执行器先净额化同方向目标再提交，成交按事前冻结的分配规则归属。行情、订单和真实可用资源始终在账户层统一管理。

## 13 尾盘买入执行设计

### 入场准入

Entry Policy消费正式计划与最新市场快照，依次验证本次运行授权、账户对账、源结果完整性、交易窗口、证券资格、盘口、行情时效、价差、市场状态、资金和容量。每次拒绝记录reason_code、触发值和对应阈值。计划加载成功并不意味着所有标的都会成交。

迟到计划以实际LOADED时间计算剩余窗口。例如14:40发布且14:40:02准备完成，可从该时刻进入执行；14:54:00准备完成时距截止仅90秒，小于120秒最小窗口，记录MISSED_ENTRY_WINDOW。因低流动性放弃的额度保留为现金，重新分配必须由明确策略规则与原总预算约束。

### 限价与容量

正常阶段使用带上界保护的限价买单。基础价来自最新卖一和可用档位；计划参考价只作为允许偏离的基准。最终价格同时受日涨跌停、连续竞价有效申报范围、max_chase_bps和max_spread_bps约束，按最小价位向买方安全方向取整。

单子委托数量取剩余目标、单笔最大金额、最近60秒新增成交量允许参与数、可用盘口容量及合法数量约束的最小值。L1档位变化不能证明自身排队位置，因此盘口容量只作为保守限制，成交仿真使用区间结果。

参与率分母使用窗口累计成交量差，并处理日切、重连和计量单位。首期按最近60秒市场成交量上限3%作为模拟工程初值，盘口可见对手量上限10%，每股票同向一个活动单、账户最多3个活动单。参数经回放和目标股票容量校准后冻结。

### 拆单状态机

Entry任务状态为WAITING、ELIGIBLE、ORDER_ACTIVE、WAITING_CANCEL、PARTIAL、FINISHED、SKIPPED。正常阶段每20秒检查子单是否需要调整；加速阶段检查周期缩短至10秒。只有报价、时窗或容量变化足以触发调整时才发撤单，每个子目标最多3次改价；达到限额后允许剩余目标未完成。

工程初值为最大追价60bps、最大价差30bps、单笔金额上限为账户净资产2%，每股票入场金额上限5%。这些值与计划中批准的更严格参数取交集；测试样例使用零实盘授权。费用预留按目标券商费率表计算，未完成费率核实前由明确保守值限制预算。

### 执行质量记录

保存选股参考价、准备完成时arrival_price、实际派发时盘口、委托价、逐笔成交价、累计成交和未完成原因。买入滑点bps按成交价相对arrival_price计算；卖出采用反向价格差，使成本恶化统一为正值。分别报告费用、价差成本、等待时间和市场冲击估计，避免用一个总收益数字掩盖执行问题。

## 14 次日退出策略详细设计

### 指标定义

gap_pct表示当日开盘价相对经核验昨收的涨跌幅；day_return_pct表示当前价相对昨收的涨跌幅；position_return_pct表示当前价相对本策略持仓成本的收益；peak_drawdown_pct表示当前价相对本次有效观测峰值的回撤。除权日使用带生效日期的价格和成本调整记录，原始成交价保持原值。

下面提供T1_EXIT_BASELINE_V3作为可完整实现和回放的初始策略。阈值用于研究与模拟参数冻结，实盘发布必须绑定策略评估报告和批准的参数版本。提高方案质量体现在规则可测、收益口径明确与异常路径完整，阈值本身不构成收益结论。

| 规则与顺序 | 触发条件 | 目标动作 | 一次性标识 |
| --- | --- | --- | --- |
| 高开减仓 | 09:30后首个有效盘口确认gap_pct达到3% | 把该批次目标持仓减至盘前数量的50% | lot_id加OPEN_REDUCE |
| 全部止盈 | day_return_pct达到7% | 目标剩余持仓为0 | lot_id加TAKE_PROFIT |
| 峰值保护启动 | day_return_pct曾达到3.5% | 记录armed与后续峰值 | lot_id加PROFIT_ARM |
| 峰值回撤退出 | armed且peak_drawdown_pct达到1%，连续有效观测持续3秒 | 目标剩余持仓为0 | lot_id加PEAK_EXIT |
| 10:30弱势退出 | 10:30后首个有效行情的day_return_pct低于3.5% | 目标剩余持仓为0 | lot_id加TIME_1030 |
| 11:00亏损退出 | 11:00后首个有效行情的position_return_pct不高于负2% | 目标剩余持仓为0 | lot_id加TIME_1100 |
| 下午收尾 | D1的14:30起仍有剩余可卖数 | 限价拆单退出；14:55:30后管理在途 | lot_id加FINAL_EXIT |

同一循环同时满足多个卖出规则时，取更低的目标剩余持仓，生成一个净卖出目标，并保留全部触发原因。高开卖一半采用“目标降到初始数量50%”，按合法股数和可卖数调整，重启后不会重新卖当前数量的一半。已经有活动卖单时，新目标只更新待执行目标。

### 状态与跨日恢复

PositionLot包含初始股数、成本基线、可卖日、剩余数量、规则触发记录、profit_armed、peak_price、peak_observed_at、行情完整性和exit_policy_hash。触发一次性动作及其意图必须在同一事务保存。peak状态定期保存，并在触发关键意图时一起落盘。

恢复时使用已持久化状态、归档完整片段和可信行情数据重建峰值。若重启缺口内的价格路径不可验证，peak规则进入PATH_UNCERTAIN，显示原因并要求按持仓批次确认恢复；时间退出与最终退出仍可在账户、行情和本次运行授权重新通过后使用。任何重启均先进入READY_PAUSED。

### 卖出执行与残仓

卖出报价受买一、跌停价、有效申报范围、价差与价位约束。系统重算可卖数和已冻结数量后创建子委托。部分成交持续减少剩余目标；撤单等待中继续接收成交。日终剩余仓位登记RESIDUAL，记录停牌、缺少对手盘、可卖数不足、委托未知或人工冻结等原因。

残仓跨日继承策略归属与未完成退出义务，下一可交易日先对账再尝试受控退出。D1退出计划的到期不会清除该义务。Shadow规则使用独立模拟账户状态和预算，不能与真实策略共享持仓可卖数或规则锁。

## 15 行情接入与Tick归档

### 数据来源与新鲜度

Market Gateway使用xtdata单股Tick订阅及get_full_tick补充快照，证券信息与交易日历在盘前准备。订阅集合为计划股票、真实持仓及必要指数；股票上限15、指数上限3。本版不把L1 Tick等同于交易所逐笔成交，保存的是SDK实际送达的行情观察[S01][S02]。

订阅槽位先保障真实持仓和活动委托，其余按计划优先级分配；15只股票按去重后的并集计算。新候选超过剩余槽位时登记SUBSCRIPTION_CAPACITY_LIMIT，保留已有持仓所需订阅。残仓释放前不会因新计划到来而丢失其行情监控。

每条Tick包含symbol、source_time、received_wall_time、received_monotonic_ns、source_session、ingest_seq、last、累计量额、档位、原始状态码及单位版本。Gateway对价格和数量单位做规范化，原始字段同时进入归档。每个交易日与重连阶段重新检查累计量倒退、重复包和时间量级。

行情健康分为FRESH、STALE、GAP、INVALID。报价容忍时间必须按真实推送周期设定：默认研究初值为5000ms，再与目标证券推送间隔P99加安全余量校准。固定1500ms可能误伤本身低频推送的行情源。相同价格的有效新快照可更新传输新鲜度；只返回陈旧时间戳的数据不能视为新报价。

### 归档文件

tick recorder接收engine的原始副本，按trade_date、symbol、source_session分区，每60秒或16MiB轮换一个Parquet文件。先写唯一临时名，关闭校验footer、行数、时间范围和SHA256后原子发布文件及manifest。进程崩溃的未完成分片隔离保存，记录对应序号缺口。

manifest包含schema_version、证券、来源、首尾ingest_seq、首尾时间、行数、重复数、缺口区间、字段单位、压缩格式、文件hash。研究读取必须携带质量标记，回放按received_time与ingest_seq重建系统所见顺序，并可额外使用source_time研究市场延迟。

### 容量与保留

以15只股票、每只每秒2条、每个交易日14400秒、每条按1KiB未压缩估算，每日约0.41GiB，20个交易日约8.2GiB。若每秒10条，则约2.06GiB每日。压缩率与SDK频率通过实测确定，磁盘按更高峰值和备份空间预留。

本地完整收到的Tick保留20个交易日，已确认上传归档目的地的文件可按清单到期处理。与订单、故障和策略评估有关的证据片段单独标记保留。归档磁盘达到90%或可用空间不足10GiB时停止新归档分片并告警，engine继续管理真实订单；若正式研究验收要求完整数据，当日Shadow结果标记无效。

## 16 风控与交易控制

### 运行模式与有效能力

环境模式取READ_ONLY、PAPER、SHADOW、ASSISTED、LIVE_EXIT_ONLY、LIVE；运行状态取BOOTING、RECONCILING、READY_PAUSED、RUNNING、HALTED、MANUAL。环境模式决定可使用的Gateway和授权上限，运行状态决定当前是否允许动作，二者分开保存。

最终有效能力由本地硬限制、环境模式、已签名计划、本次运行授权、人工控制和健康约束求交集，分别计算can_buy、can_sell、can_cancel和can_query。SELL_ONLY等动作按能力集合表达，避免用一个整数比较所有模式。任何来源都只能在其授权边界内收紧或恢复能力。

### 每次派发前检查

| 类别 | 硬检查 | 拒绝或降级范围 |
| --- | --- | --- |
| 身份与执行者 | 账户Mutex、节点代际、QMT账号、发布签名 | 账户全部新派发 |
| 交易许可 | 当前能力、permission_epoch、有效时窗 | 对应方向或股票 |
| 数据完整性 | 正式来源、证券规则、行情、账户观测窗口 | 对应计划或股票 |
| 风险资源 | 现金、组合与单票暴露、可卖量、预占 | 超出部分或整单 |
| 订单确定性 | UNKNOWN集合、活动单互斥、撤单在途 | 受影响股票；账户资金不明则全部买入 |
| 系统健康 | Journal可写、事件缺口、时钟和SDK健康 | 按故障矩阵冻结 |
| 交易行为 | 单笔金额、每秒速率、日累计报撤单数 | 对应账户动作 |

### 试点限额与变更

首次实盘启用的参数包必须明确账户总投入、最大总仓位、单股金额、单笔金额、股票数、报撤单频率、日最大委托数、日风险预算和授权有效期。示例模拟包设置总仓位30%、单股5%、最多3只、单笔2%，因此在只有3只时实际理论上限为15%；总上限是保护值而非买满目标。正式资金数由账户所有者批准并写入签名参数包。

配置分为产品参数、策略参数和本地Hard Safety。产品参数管理网络与路径；策略参数定义交易意图；本地Hard Safety定义不可被计划扩大的边界。收紧限制可以即时生效，扩大实盘能力需新的本次运行授权和账户核验。运行中配置变更产生新hash和版本事件。

### 控制动作语义

| 动作 | 新买单 | 新卖单 | 活动订单 | 生效条件 |
| --- | --- | --- | --- | --- |
| PAUSE_BUY | 停止 | 按原许可 | 继续管理 | 本地或授权远程命令 |
| SELL_ONLY | 停止 | 允许已授权卖出 | 继续管理 | 健康检查仍生效 |
| HALT | 停止 | 停止 | 保持观察并显示在途集合 | 急停即时锁存 |
| CANCEL_AND_HALT | 停止 | 停止 | 对指定可撤委托发撤单并逐笔回执 | 先锁存HALT，后执行撤单 |
| MANUAL_TAKEOVER | 停止 | 停止 | 按交接单列出归属及在途状态 | 人工接受交接结果 |
| RECONCILE | 原许可 | 原许可 | 查询；必要时设置差异锁 | 同一账户单次对账 |
| RESUME | 经检查恢复 | 经检查恢复 | 先确认全部在途 | 本地确认、当前状态版本与完整恢复报告 |

HALT动作不隐含新的风险卖单。操作者在页面可明确选择“停止自动交易”或“停止并撤销指定委托”。真实委托可能继续成交，因此页面分别展示自动派发已停止、撤单完成数、未确认数和剩余风险。

### 控制确认与远程顺序

已认证本地用户点击HALT直接触发，engine先关闭派发闸门，再记录审计并返回有效能力及在途摘要。一般撤单、策略切换和恢复需要影响预览与二次确认；预览携带state_version和短期nonce，状态变化后重新预览。

远程命令包含command_id、command_seq、scope、action、expected_state_version、issued_at、expires_at、operator和reason。收紧命令可在序号缺口时优先生效；扩大能力的命令等待缺口补齐并核验当前scope版本。APPLIED表示状态变更完成，撤单集合未全部终结时返回PARTIAL或IN_PROGRESS。

本地HALT由独立锁存记录与Journal共同表示。解除仅在本地操作并重新完成对账，本地恢复不会清除仍有效的其他健康锁。权限变化通知SDK派发闸门，以同一permission_epoch消除异步线程持有旧许可的竞态。

### None与查询一致性

None被转换成UNCERTAIN或UNAVAILABLE，并保留原返回类型。健康连接与账户状态正常是必要条件，但不能单独证明某次空结果完整。只有经实际空账户、非空账户、断线、收盘及恢复场景验证，能够明确表示完整空结果的返回才映射AVAILABLE_EMPTY。

Broker查询使用一个请求队列，按委托/成交优先、资产/持仓随后执行。查询超过5秒即显示超时并冻结相关新派发；底层返回后按原query_id处理，过时观测只进历史事实，不覆盖较新已确认视图。连续失败触发连接恢复。

### 重连流程

收到交易断线后立即收紧派发权限，保留未确认订单。恢复协调器退避连接，重新订阅账户，查询四类事实，与本地提交和成交集合核对。健康连续观察与对账通过后进入READY_PAUSED，由本地恢复会话授权决定可用能力。

QMT是券商终端进程，supervisor在故障时告警并管理自己的子进程；重启QMT属于独立操作预案，需要先记录账户在途情况与登录恢复条件。生产QMT版本升级在维护窗口完成，其前后接口形状与行为回归进入发布报告。

## 18 对账与交易账单

### 三层对账

执行对账比较本地提交、券商委托和成交；库存对账比较成交计算的持仓与券商总量/可卖量；财务对账比较成交、费用、资金流水、企业行为和正式交割账单。三个结果分别为PASS、DIFFERENCE、INCOMPLETE，不能用其中一个PASS代表全部完成。

对账于启动、交易重连、提交未知、发现外部交易和盘后触发。盘中每2秒查询活动单，成交后的持仓观测合并为最多每5秒一次，稳定期持仓15秒、资产30秒。主动查询受单并发及券商实际限制控制，繁忙时合并重复请求。

### 观测窗口算法

对账先记录本地事件序号L0，再查询委托、成交、持仓、资产，最后记录L1。如果窗口内出现可能改变资产或数量的事件，回放该窗口事件并再次查询关键集合；连续两次结果稳定且相关交易事实已接收时，形成一致快照。无法取得稳定窗口则报告INCOMPLETE并附差异，保持保守交易能力。

中心对账请求固定ledger_version和node_event_watermark，待投影追到该水位后比较。中心投影落后造成的差异标记PROJECTION_LAG，重放完成后复核。市场浮动造成的市值变化和真实股数差异采用不同分类。

### 差异处理

| 差异 | 处理 | 解除条件 |
| --- | --- | --- |
| 本地未知、券商存在的订单 | 通过短令牌和关联事实恢复；归属不明转人工 | 归属确认、数量与预算对齐 |
| 本地提交、券商未查到 | 保留UNCERTAIN并扩大查询范围 | 明确未发送或最终裁定证据 |
| 漏成交或重复成交 | 按券商唯一键补录或去重 | 订单累计量与持仓一致 |
| 人工买卖 | 创建EXTERNAL归属，冻结相关策略派发 | 交接与虚拟持仓调整完成 |
| 股数或可卖差异 | 对应股票锁定，检查T+1和冻结量 | 成交、企业行为与可卖事实完整 |
| 资金差异 | 区分活动单冻结、费用、转账和时间差 | 各组成项目可解释 |

### 正式账单流程

15:10生成盘后交易快照与PROVISIONAL日报。agent按券商可用时间获取正式成交交割单和资金流水，或由操作员上传券商导出文件；上传交易中心后按文件hash去重，校验账户、期间、币种、行数与金额，产生导入预览，核准后生成SETTLED账本版本。

export_data或query_data属于QMT通用数据能力，是否提供正式交割单、历史范围及真实费用取决于券商版本。正式账单适配器使用独立的数据类型与文件Schema，能力未验证时使用人工导入流程，日报明确显示费用待核实。

更正账单采用新import_id并引用replaces_import_id，创建冲销或调整凭证，保存原始文件和旧账本版本。跨日未解决的订单和资金差异保留OPEN状态并带到下个交易日。所有日终结果使用真实交易日标识。

### 收益口径

交易中心保存不可变凭证，借贷金额相等。买入减少现金并增加股票成本，卖出增加现金、结转成本并确认收益；佣金、税费和其他费用单列。企业行为与入出金具有独立凭证类型。策略成本采用按持仓批次分配，账户净值按券商正式资产与现金流核对。

简化日损益为期末权益减期初权益减净入金，其中净入金为入金减出金。存在日内现金流时，收益率使用时间加权分段链接；没有分段估值时输出Modified Dietz估计及估计标记。回放使用当时可见数据与费用模型，正式账本的最终费用不回写成历史交易时已经知道的信息。

## 19 中央数据模型与数据治理

### 表组和唯一约束

交易管理中心采用独立schema trade_control。API层做身份和结构校验，应用服务组织事务，Repository层封装SQL。原始事件保留不可变正文，投影可以从事件重建，财务更正使用附加凭证。

| 表组 | 关键表 | 主要唯一键与索引 |
| --- | --- | --- |
| 身份与授权 | nodes、accounts、node_keys、execution_grants | node_id；account_id；key_id；grant_id |
| 选股与计划 | selection_snapshots、plans、allocations、plan_receipts | 源run加revision；plan_id；发布业务键 |
| 策略与规则 | policy_bundles、rulebooks、config_versions | bundle_id加version；content_hash |
| 原始事实 | raw_events、event_receipts、projection_jobs | event_id；node加代际加event_seq |
| 订单投影 | orders、order_attempts、fills、reservations | client_order_id；券商订单键；券商成交键 |
| 持仓与观测 | position_lots、snapshots、snapshot_parts | lot_id；snapshot_id加part_no |
| 账单与凭证 | statement_imports、journal_entries、journal_lines | 文件hash加账户；entry_id；来源事实键 |
| 治理与恢复 | commands、command_receipts、reconciliations、incidents | command_id；对账ID；事件指纹 |

原始事件表按account_id、trade_date、event_seq建立检索路径，投影Worker每次锁定最多200个待处理任务，事务时长目标低于100ms。首期单Worker顺序处理同一账户，保留账户分区字段以扩展。重建采用新projection_version，验证后切换查询视图。

### MySQL事务和可靠性

使用InnoDB本地事务、唯一键及受影响聚合的行锁。接收成功以事务COMMIT成功为条件；投影失败不回滚已接收原文。启用binlog，采用innodb_flush_log_at_trx_commit=1及sync_binlog=1，并验证存储层同步写能力[S10]。API数据库连接池初值5、突发增加最多5，Worker独立小连接池；全表重建和报表导出使用维护预算。

中央单实例数据库仍有服务故障风险。Windows本地交易依赖已冻结计划与Journal，因此中央维护窗口不成为已授权订单处理的实时依赖。中央恢复RPO目标5分钟、RTO目标30分钟；节点保留已确认事件至少90日，并在中央恢复后校验接收水位，必要时补回旧事件。

### 数据保留

| 数据类别 | 节点保留 | 中央与归档 |
| --- | --- | --- |
| 未上传事件、未知订单与开放Incident | 保存到解决且中心确认 | 保留原始事实及处置链 |
| 已确认订单、成交与控制Journal | 在线90日；旧数据按完整性清单归档 | 原文及财务凭证工程默认5年 |
| 执行过的计划与策略包 | 持仓结束后至少90日 | 版本及审批记录长期保留 |
| 普通运行日志 | 30日滚动 | 告警与故障片段按事件归档 |
| 完整收到的Tick | 20个交易日 | 研究默认1年；关键证据随事件保留 |
| 日备份 | 20个交易日 | 每日35日、月备份12个月 |

期限为工程配置，正式启用时与券商、数据授权及适用留存要求核对后冻结。开放案件与未完成恢复覆盖普通到期策略。所有清理作业先生成清单、校验已归档hash与保留锁，再在明确产品数据根目录中处理；文件路径解析必须拒绝越界与重解析点跳转。

## 20 本地操作台与中央页面

### 本地操作台

本地台由node agent在127.0.0.1托管，Edge应用模式快捷方式打开。概览每秒读取一次带state_version的只读快照，查询与详情可分页；核心不可用时页面展示最后已知时间、supervisor状态与应急步骤。交易内核独立运行使页面刷新、关闭和升级具有清晰边界。

| --- | --- | --- |

### 中央页面

中央台包括账户与节点总览、计划发布、订单追踪、持仓差异、财务日报、执行质量、策略版本、授权与密钥、Incident和发布记录。总览按账户显示最后心跳、现场模式、中心意图与节点实际状态，明确远程命令仍在传递时的风险。

计划详情支持从正式源run跳到签名计划、分配、意图、委托和成交。日报区分PROVISIONAL与SETTLED，提供账本版本与费用差异。执行质量展示完成率、滑点分布、撤单比例、容量限制、错过窗口和每条Exit规则贡献；报告保留样本数和市场环境。

### 页面安全

本地用户身份经受保护凭证验证，使用HttpOnly、SameSite=Strict短会话、CSRF token、Origin/Host校验和请求限速。敏感动作绑定账户、scope、state_version、有效期和确认nonce。HALT对已认证本地操作即时响应，恢复和撤单采用影响预览。

中央操作角色为只读、交易操作、策略发布、风险授权和运维。扩大实盘额度、切换有效策略与变更节点身份需要创建人与复核人不同；HALT和收紧权限允许授权操作者直接执行。单人试验账户通过事先签署的限额和会话授权简化日内普通操作，重大权限扩展仍记录明确责任人。

## 21 部署发布与现场运行

### Windows安装

程序存于 C:\Program Files\AutoTrading\releases\<version>，可变数据存于 D:\AutoTradingData\<account_alias>，Tick优先存独立归档盘。安装清单列出绝对路径、文件hash、进程入口、命名管道、任务名称和账户权限。真实账户号保存在受保护映射中，目录只使用别名。

采用专用Windows11或Windows Server2022受支持x64环境，QMT与engine在经PoC验证的同一用户登录会话运行。Task Scheduler负责supervisor的启动与存活检查；节点工作日长时间运行，电源与更新策略在维护窗口配置。不同Windows会话之间的账户互斥使用Global Mutex，并校验对象DACL。

supervisor重启时通过进程创建时间、可执行路径hash、账户、启动代际和IPC握手识别现存engine。它先接管监护，再决定是否拉起缺失进程。engine存活但IPC失联时先设置外部HALT并告警，不能依据PID文件直接产生第二个交易进程。

### 发布清单

ReleaseManifest包括源commit、构建环境、Python/SDK/APSW/SQLite版本、wheel与前端hash、Schema版本、策略代码包hash、配置hash、迁移清单、兼容矩阵和测试证据。安装与启动均校验清单。应用程序与策略实现仅在维护窗口更新；盘中可变参数遵循控制协议与风险约束。

发布分为构建验证、目标只读检查、停新派发并结束在途、备份、应用切换、恢复对账和本地授权。旧应用包保留，交易事实不回滚。数据库使用扩展后切换的兼容迁移；旧应用只能读取其明确支持的Schema，不能为了代码回退恢复一份覆盖新交易事实的旧数据库。

### 凭证与网络

Windows仅主动访问管理中心和必要的基础设施地址。QMT登录凭证、本地认证凭证及HTTP节点密钥采用Windows Credential Manager或DPAPI保护。管理中心用独立服务账户与数据库账号，计划签名密钥采用受保护的秘密存储。源代码、普通日志与故障包仅保留密钥ID和账户别名。

密钥轮换先分发信任配置，再发布新版本，最后按有效期撤销旧密钥。节点长时间离线时旧授权到期后失效，恢复同步并重新核验才可获取新授权。操作者管理员权限或专用用户凭证被完全攻陷属于操作系统信任边界失效，应用层ACL不能消除这一风险。

### 实盘环境前置证据

实际交易前登记目标机器、券商账号权限、程序化交易报告确认、可交易市场、QMT版本三元组、金额与证券范围、值守联系人及会话授权。上交所现行报告要求将首次开展程序化交易前的会员核查确认作为条件[S11]；具体账户的适用流程由券商确认并留档。

这些条件约束真实接入与真实委托阶段。领域代码、Mock/Replay、协议、页面、进程隔离和持久化故障测试可以独立推进，待验证的现场属性通过能力报告替换模拟输入。

## 22 监控故障与恢复标准

### 监控指标

指标分为交易安全、数据时效、系统资源和业务完成四类。engine每秒发布内部健康快照，supervisor独立观察进程与心跳，agent每5秒上报中心。中央按账户聚合同一根因告警，记录首次发生、最后发生、影响范围和处理人。

| 指标 | 工程目标或告警线 | 处理 |
| --- | --- | --- |
| 重复自动委托与未解释成交 | 0 | P0，停止相关自动派发并保留现场 |
| 决策循环排队P99 | 20ms以内，连续超限5秒告警 | 冻结新入场，分析队列与耗时 |
| 关键事务提交P99 | 50ms以内，应用等待250ms | 超时进入PERSISTENCE_UNCERTAIN |
| 计划发布至节点LOADED | 健康网络P95在3秒内 | 检查轮询、签名与写入分段耗时 |
| 核心心跳 | 每1秒，5秒未更新 | supervisor锁存故障并诊断 |
| 中央事件可见延迟 | 健康网络P95在3秒内 | 区分上传与投影延迟 |
| Outbox最老未达事件 | 30秒告警，5分钟升级 | 检查连接与容量，不丢弃待传原文 |
| 行情时效 | 按证券推送周期校准 | 对应标的暂停依赖行情的派发 |
| 时钟偏差 | 1秒告警，超过2秒锁定新买入 | 重校时间及边界时段规则 |
| 恢复到READY_PAUSED | 常规进程故障目标120秒内 | 超时升级，真实自动恢复另行授权 |

以上为目标机验收目标，券商受理和成交延迟单独观测。节点无法确认真实成交的原因可能为市场与柜台，处理时间不能等同于保证成交时间。

### 故障矩阵

| 故障 | 立即行为 | 继续能力 | 恢复条件 |
| --- | --- | --- | --- |
| 量化来源失败 | 中央记录来源不可用 | 已有持仓与已授权计划 | 正式新结果及有效窗口 |
| 中央断网 | Outbox重试并显示离线 | 本次已ARMED且仍有效的计划与退出 | 网络恢复、验签与同步核验 |
| agent崩溃 | supervisor单独重启agent | engine继续管理；本地应急CLI可用 | agent重新握手与恢复游标 |
| recorder故障 | 标记归档缺口 | 交易核心与Journal继续 | 新分片校验并记录缺口 |
| Journal失败 | HALT全部自动新报单 | 事实采集尽力缓存，券商终端人工处理 | 存储健康、事件补偿、券商对账 |
| QMT断线或查询不明 | 冻结相关派发并保留在途 | 已接收事实和本地控制 | 重连订阅、完整查询、对账和授权 |
| SDK卡死或核心崩溃 | 外部HALT、确认旧进程生命周期 | 中央与agent可显示最后状态 | 唯一新进程、恢复对账和本地确认 |
| 行情缺口或无效 | 锁定受影响规则 | 不依赖缺失路径的监控和查询 | 新鲜行情及指标重建 |
| 发现外部交易 | 冻结对应标的，资金不明冻结买入 | 其他明确安全的持仓管理 | 归属与预占对齐 |
| 单盘物理损坏 | 停止自动交易 | 通过券商终端核实与操作 | 备份加中心事件加券商历史恢复 |

### 本地应急入口

发布包提供受ACL保护的CLI，用于查询supervisor状态、设置HALT、导出诊断和请求对账。CLI通过独立控制管道访问engine或supervisor，agent崩溃时仍可设置外部HALT。全机或QMT不可用时，操作员通过券商正式客户端与券商支持渠道处理真实账户。

恢复报告必须列明未确认提交、活动委托、当前持仓、现金预占、未上传事件、策略状态完整性与有效控制锁。所有未知项有最终处置，恢复从READY_PAUSED开始。自动重启只恢复软件运行，实际交易许可由本次会话授权决定。

### 性能与耐久测试

以15只股票加3个指数、实际推送速率10倍、订单回报突发、代理断网重试和归档并发作为组合负载。持续运行至少两个完整交易日长度，检查P99延迟、RSS增长、队列水位、WAL维护及消息完整性。验证关键控制在高负载下仍可处理。

进程强制退出只能证明进程崩溃恢复。断电持久性需要在专用测试机或虚拟机存储故障注入中验证，并核对磁盘缓存与同步写行为。测试使用隔离数据目录和模拟账户，清理仅针对本次测试清单。

### 上线阶段

模拟闭环通过后进入目标只读；目标只读通过后至少20个交易日Shadow，期间覆盖迟到计划、无候选、部分行情缺口与日切。随后进行不少于5个交易日的受限ASSISTED，使用可交易的最小合法数量与已批准金额，验证真实撤单、费用和持仓。

LIVE_EXIT_ONLY在账户持仓归属明确时验证自动退出；完整LIVE按账户金额、股票数、仓位中的一个维度逐次调整。升级条件为无未解释成交、无自动重复单、数量对账一致、故障已归因且形成回归。样本不足时继续观察，不以日期到达自动升级。

这是一版针对新架构的估计。计划调整基于每个阶段的实际交付速度与缺陷，不能按已有文件数量直接折算剩余工期。优先完成V3-008最小启动闭环，可尽早暴露装配、持久化和状态之间的系统性问题。

### 推进记录

每个工作包分别记录implementation_status、verification_status、field_status和release_status。implementation可为TODO、IN_PROGRESS、DONE；verification可为PENDING、PASS、FAIL；field可为NOT_REQUIRED、PENDING、PASS；release可为NOT_READY、READY。阻塞记录填写缺失对象、影响的具体验收项、当前可继续任务及解除证据。

每次交付记录提交ID、构建hash、测试命令与结果、设计决策ID、协议或Schema变更、遗留问题和下步任务。开发完成时只改变相关状态，真实账户未验收时不会标成“可实盘”。新版工作包与旧计划分开登记，采用本方案实施后再建立映射。

## 25 设计决策与实施差异

### 关键决策记录

| 决策 | 采用内容 | 需要承担的成本 |
| --- | --- | --- |
| D01 | 交易中心独立服务与MySQL实例 | 多一套部署、备份与身份治理 |
| D02 | Windows四进程、单一交易核心 | 需要IPC协议、进程监护和系统级测试 |
| D03 | APSW固定SQLite版本和Owner单连接 | 数据库任务显式排队与性能维护 |
| D04 | 模糊提交保持未知并人工裁定 | 部分故障场景会错过交易机会 |
| D05 | 计划有冻结离线授权 | 远程撤回在节点离线时不能即时生效 |
| D06 | 持仓批次与退出策略跨日保存 | 需要跨日账本、企业行为和残仓处理 |
| D07 | 完整归档收到的Tick并保存缺口 | 独立磁盘预算与研究质量检查 |
| D08 | 同一标的一策略持仓归属 | 未来跨策略共持需要分配账本扩展 |
| D09 | 每次重启回到READY_PAUSED | 需要值守响应和本地会话恢复 |
| D10 | 以业务闭环与证据判断完成 | 需维护可运行演示、故障矩阵和发布报告 |

### 与当前目录中方案的主要差异

当前V2.4采用量化服务内部自动交易增量和Runtime内同步、控制台、Recorder Worker。本版把中央管理服务独立部署，并把Windows代理与归档移到独立进程；其目标是获得可以分别限额和重启的边界。这会改变部署与IPC装配，但不会改变券商事实优先、标准化计划和本地意图持久化的基本需求。

当前开发计划中存在正式14:40结果的发布实现描述，而多处业务流程沿用14:31产出、14:35启动。新版以正式结果事件与剩余窗口为准。节点程序入口当前仍以版本和配置诊断为主，多个操作台页面仍为后续交付项；因此后续实施首先验证可启动业务闭环，不能用模块专项通过替代系统装配验收。

现有领域类型、签名测试、Mock、部分Journal和订单测试可作为行为参考，具体复用必须通过新版端口与不变量验收。代码复用率是实施时的结果，不是本版架构决策依据。已有协议V1与本版API V2属于独立版本，切换需要双向兼容测试与明确切换窗口。

### 采用新版时的切换安排

先在独立测试数据目录完成新版中央与节点模拟部署，使用回放输入进行行为对照。原量化服务只增加或启用正式结果读取契约，交易管理通过独立地址提供。旧版交易模块保留为现状，不参与新版运行；实际关闭或迁移旧模块在实施工作包中按精确文件、配置和数据库清单执行。

旧有交易事实若存在，则先导出不可变清单与hash，导入新版后核对订单、成交、持仓和财务总额；未核对前保持旧数据可读。运行切换先停止旧执行者并确认账户在途，再提升新的节点generation。主机失联时单凭租约过期无法证明它已停止，必须有现场停止或券商会话失效证据。
