# ADR-R31-004 历史流式核验与检查点分片

日期：2026-09-21。状态：dev44离线实现采用；长期文件轮换和目标机负载继续验收。

## 1 采用方案

恢复过程采用“完整历史分页核验、当日J1有界留存、存续批次目标压缩”的方式。恢复与收盘检查点采用“逻辑正文摘要、内容寻址分片、根清单最后发布”的方式。

现有SQLite/WAL继续由单一Journal线程访问，SQL Schema保持1、六表27字段。历史J1、控制、回报、检查点和未发布的孤立分片均保留。本轮优化读取和有效工作集；数据库文件轮换、备份验证、维护告警及孤立分片整理由后续维护包统一处理。

## 2 历史与当日记录的分工

恢复先读取开盘检查点并验证账户、日期、日历及逻辑正文摘要，再从J1第一条开始按每页最多200条读取。每一页仍验证存储正文摘要；引擎逐条核验账户、历史日期、序号和封存边界。

历史摘要采用增量SHA-256，输入仍为旧版规范JSON数组`[[record_seq, stored_payload_hash], ...]`，与dev42/dev43的完整数组摘要完全一致。读取跨过封存水位前，先核对完整前缀摘要和准确最大序号；遇到缺失、乱序、未来记录或未封存历史尾记录，恢复失败并保持暂停。

已核验历史记录随后释放正文引用，保留：

- 已扫描数量、最大序号和可继续计算的摘要状态。
- 开盘持仓中仍有剩余数量的批次，其历史SELL动作的最紧目标和规则版本。
- 当前交易日的完整J1记录，供订单、成交及账户核对。

历史SELL目标只向更小剩余持仓收紧，规则版本保持一致；新的SELL准入同时核验压缩历史目标和当前日子单目标。收盘再次进行完整恢复核验后，使用全历史加当日记录的摘要封存，只把仍有持仓的批次带入次日。历史订单和已退出批次证据继续存在于原Journal。

## 3 分片发布协议

不超过64KiB的规范JSON继续按原正文写入原检查点键，保留旧载荷读取方式。较大正文拆成32KiB原始字节片；单片以Base64 JSON保存，使用`checkpoint-chunk:<原始字节摘要>`作为键。相同分片复用原内容，键值冲突失败关闭。

全部分片逐个提交成功后，才向原检查点键提交`CheckpointManifest`根清单：

| 字段 | 含义 |
| --- | --- |
| storage_format | 固定`critical-blob-v1`，顶层保留字段 |
| payload_hash | 完整规范JSON正文摘要 |
| byte_count | 完整正文UTF-8字节数 |
| chunk_bytes | 固定32768字节，末片按剩余长度验证 |
| chunks | 按正文顺序排列的原始分片摘要列表 |

读端先验证根清单，再逐片验证存在性、Base64、准确长度和摘要，最后验证总长度、完整摘要和JSON规范格式。分片可能跨UTF-8字符边界，先按字节完整拼接，再解析JSON。

根清单尚未发布时，已提交的分片只是孤立材料，不构成有效检查点。根清单发布后仍以完整读取验证为准。中断重试采用同内容幂等写入；原键异内容拒绝。上层恢复或封存引用绑定的是逻辑正文摘要，与具体分片布局分离。

## 4 容量和时间边界

| 维度 | 当前工程上限 | 超限行为 |
| --- | --- | --- |
| 每次历史扫描 | 100,000条，含当日记录 | 恢复失败，维护核对后重试 |
| 每页J1 | 200条 | 拒绝异常分页 |
| 当日J1留存 | 2,048条 | 恢复失败，保持暂停 |
| 存续历史目标 | 2,048个动作 | 恢复失败，保持暂停 |
| 开盘/收盘批次 | 2,048个 | 模型验证拒绝超限 |
| 单逻辑检查点 | 8MiB、最多256片 | 写入/读取验证拒绝超限 |
| 单SQL证据行 | 64KiB | 原存储边界保持有效 |
| 暂停态完整恢复 | 30秒总时限；分页仍为5秒请求时限 | 收紧权限，迟到结果只作为存储事实 |

这些数字是明确的安全预算，而非目标机性能承诺。当前实现需要完整扫描既有历史，因此恢复耗时仍随历史数量增长；内存不再随已封存J1正文数量线性增长。文件体积和恢复启动时间的长期治理由受控轮换包继续完成。

报单J1的250ms应用等待和SQLite原100ms锁等待保持原样。检查点分片工作只用于暂停恢复与收盘封存，不放入Tick处理或普通日志路径。

## 5 发布、权限和兼容

恢复记录30秒等待期间始终保持暂停。恢复开始时冻结许可代际；等待期间发生HALT、代际变化或超时，候选报告失效。即使根清单随后落盘成功，也不会被该次恢复应用。全部证据成功后仍需本次boot的恢复确认与新授权。

小正文和原前缀摘要保持兼容。旧版本面对分片根清单无法完成新格式恢复；含此类记录的Journal由dev44及以后兼容版本读取。SQL版本未变代表表结构兼容，不代表应用层降级可直接执行。回退需在暂停状态保存完整数据库和对应版本，并验证读取能力。

新增本地Schema为`checkpoint-manifest`和`checkpoint-chunk`。日终HTTP协议、量化MySQL、业务查询页面及定时回传职责保持原方案。本轮不修改量化项目。

## 6 验证与后续

离线验收使用新建私有目录中的合成历史和Mock当日拒单事实，验证超过旧2048条历史限制的恢复、大于64KiB的正文、跨日摘要延续和默认暂停。故障矩阵覆盖缺片、格式/长度/摘要错误、半途写入、迟到发布、急停，以及专属写入子进程在分片/根清单提交后的实际强制终止。

后续顺序：关键事实有界批量提交及队列/磁盘压力→暂停态备份验证和保留源文件的代际轮换→完整engine强杀及多进程组合验收→目标机存储复验。前面三项属于可继续离线开发，最后一项需要实际目标环境。R31-005/003整包继续IN_PROGRESS/PENDING/NOT_READY。
