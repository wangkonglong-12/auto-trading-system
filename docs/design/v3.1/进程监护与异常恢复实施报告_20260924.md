# 进程监护与异常恢复实施报告

完成日期：2026-09-24。程序：0.1.0.dev49。Windows 验证基线：CPython 3.11.16。

## 1 交付结论

本轮完成新版 Mock 交易进程的独立监护切片。实际策略尚未定稿，Entry/Exit 规则继续作为模拟基线保留；本轮没有增加买卖条件、调整交易阈值或开放实盘。

| 已实现内容 | 行为与验收 |
| --- | --- |
| 独立监护命令 | supervise 启动自己的 engine；STATUS/STOP 使用独立认证管道 |
| 账户与进程身份 | 监护和 engine 各自账户互斥；已有独立 engine 拒绝接管；只管理本次创建的 Job |
| 主循环健康 | 只认 owner 发布的递增序号；管道线程仍响应而主循环卡死也会被发现 |
| 异常退出与重启 | 先停止受控进程，再保存故障；按退避间隔拉起新进程，新进程保持暂停与重新核对 |
| 持久化熔断 | 失败预算跨重启保留；默认累计3次失败停止自动重启；磁盘/身份/Journal异常直接锁定 |
| 监护自身强杀 | 已分配到Job的运行子进程随句柄关闭退出；下次启动识别未收尾记录并计失败 |
| 正常停止 | 优先绑定启动身份的限时正常退出，随后以自有Job兜底；主动停止engine不会被重新拉起 |
| 人工维护重置 | 运行身份、两类进程均停止、交互确认；旧监护状态归档保留，交易授权不变 |
| 配置与任务生成 | 新增带说明的监护配置；Engine任务仍沿用原名称，生成的动作改为supervise；实际注册另行执行 |

实现和字段定义见[ADR-R31-008](ADR-R31-008_策略无关的进程监护与恢复.md)。Windows虚拟环境启动器与实际解释器分别校验：回复通过认证后，还必须证明实际PID属于本次Job。

- 新增65项监护专项；全量2,254项Python测试通过，综合覆盖率91.33%。
- 新增监护状态机覆盖率96.76%，Windows进程所有权模块93.69%，监护持久化模块96.92%。覆盖率包含分支，真实子进程测试另有行为断言。
- Ruff检查、格式检查和mypy通过（321个Python文件）；配置Schema、V2契约、仓库凭据边界及Windows任务脚本检查通过。
- 前端24项测试、类型/格式检查及构建通过，使用符合项目要求的Node 24.19.0。此前系统默认旧Node导致测试工具无法启动，切换到既有兼容运行时后完成验证；前端业务代码未改动。
- 独立wheel安装后的341项监护/进程/授权/业务组合/买入/退出专项通过；安装来源和源文件一致性由制品验证脚本检查。七个既有离线模拟入口及最终制品记录见本轮artifact-verification.json。

覆盖的故障包括主循环停滞、初始进度超时、重复/倒退序号、错账户/节点/代际/启动身份、进程异常退出、监护器强杀、低磁盘空间、故障状态写入失败、损坏状态、重复监护、已有engine、正常停止及重置保留证据。

2026-09-23的2,246项首轮结果保留在原目录。用户关机后，尚未取得最终输出的追加测试和前端验证重新执行；本报告以`evidence/r31/20260924-supervision/`下最终结果为准。此次开发机器关机后的代码恢复，不等同于目标QMT机器关机/登录场景的正式验收。

## 3 文件和数据边界

本轮改动集中在本项目的进程监护、进程状态、受限本机通信、配置Schema、任务定义、专项测试和设计/开发记录。量化后台没有本轮写操作；生产数据库、凭据、真实QMT、Windows已注册任务保持原状态。

数据库结构保持不变。监护信息写入受保护的`critical/supervision-state.json`，不放在可轮换的普通日志目录；正常健康查询不写SQLite。Tick继续按原内存路径处理。维护重置会先归档旧状态，未删除业务恢复记录。

已对上一轮留存文件清单及本次重启后清单执行只读比对，原有文件删除0个。上一轮清单对比包含dev48和dev49两轮新增/修改，不能把全部差异归因于本轮；相关范围在证据README中说明。
