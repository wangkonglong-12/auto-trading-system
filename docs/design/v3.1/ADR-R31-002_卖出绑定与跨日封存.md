# ADR-R31-002：卖出绑定与跨日封存

日期：2026-09-21。状态：用于dev42离线执行内核；正式生产组合按R31验收门接线。

## 决策

1. `Submission.sell_binding`采用版本1载荷，包含责任策略、开盘持仓检查点摘要、有序批次分配和随本次提交保存的已触发规则。它与原动作目标、报单意图位于同一个J1正文、同一次事务。旧记录缺少该字段时保持原序列化正文和摘要；恢复可以读取旧格式，SELL执行要求完整绑定。
2. 当前D1动作按单批次定义，稳定动作ID绑定账户、策略、批次和`T1_EXIT_BASELINE_V3`。子单数量以批次原始目标计算，连续子单沿用该动作且目标单调收紧。已确认的成交扣减持仓，活动子单未成交量预占，终态核对后释放余量。
3. 每个交易日15:00后，engine在暂停、SDK空闲、关键事实处理完成、全部本地意图已由券商终态解释、最新账户观测核对成功时，生成`PortfolioCheckpoint`。正文保存在原`recovery_checkpoints`，键为`portfolio-close:YYYY-MM-DD`；账户、交易日、日历版本、CLEAR恢复报告摘要、已覆盖J1最大序号及全前缀摘要、持仓批次一并冻结。该boot从申请封存起保持暂停。
4. 次日组合根提供上一交易日的`OpeningReference`。engine通过同一个账户Journal读取封存正文，校验摘要、日历连续性和全部历史J1前缀，分开已封存历史与当日意图，再查询券商当日委托、成交和持仓。历史缺失、封存后仍有未覆盖的旧日意图、跨账户/错日历或实际持仓不符均进入失败/阻塞状态。
5. 开盘检查点是本地持仓恢复证据，权限来自本次boot的新恢复确认和SELL会话授权。正式HTTP日终协议及量化MySQL保持当前结构。新增的两个本地Schema描述封存和引用格式；中央端的批次级审计导出继续按独立契约修订交付。
6. `exit_execution`将D1纯规则结果转换为候选子单，最终仍由engine、预占、J1和SDK派发边界核验。重启恢复已落盘目标及规则，峰值路径设为`PATH_UNCERTAIN`，单调时钟及持续回撤计时重新开始。没有触发子单的规则状态转移由后续策略owner独立持久化，这一完整循环仍为工程待办。

## 兼容性与容量

最小Journal继续六张表、27个字段，SQL Schema版本保持原样；新增字段位于带版本JSON正文并具备用途注释。已有无绑定J1的摘要及重复提交判定保持兼容。旧程序对新SELL字段会严格拒绝解析，因此升级后产生新SELL记录的Journal使用dev42及后续兼容版本恢复；软件回退采用只读封存、兼容读取验证和发布级回退流程。

当前读取完整Journal前缀的上限仍为2048条，单个检查点仍限64KiB。这是开发阶段明确的有界失败上限，分段证据、历史轮换与长期保留由R31-005继续完成。新增载荷只保存关键归属和恢复证据；Tick、行情窗口及普通日志沿用各自路径。

## 正式运行接线前条件

- 开盘前可用的退出授权/策略上下文，由正式组合根提供并验签；尾盘买入计划仍按Windows原定时拉取流程取得。
- 正式日历、前收/开盘/复权成本来源，行情新鲜度、市场时段与数量/价格规则的组合校验。
- 无子单和在途期间的目标/规则状态持久化，峰值路径重建与完整D0至D1回放。
- 本机认证IPC、任务/封存引用发布、快照日终导出以及人工/企业行为差异处置。
