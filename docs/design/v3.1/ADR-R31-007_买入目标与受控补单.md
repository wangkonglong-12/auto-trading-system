# ADR-R31-007 买入目标与受控补单

日期：2026-09-23。状态：dev48离线实现采用；独立进程策略装配与现场准入继续验收。

## 1 采用的结构

Entry沿用引擎单一状态所有者、内存行情、唯一Journal写者和独立SDK工作线程。职责分为：

| 组件 | 职责 |
| --- | --- |
| entry_state | 已安装策略/证券规则模型、一次目标、不可变保存与恢复 |
| entry_gate | 行情时效、价格与数量规则、目标引用和子单限制；SDK派发前再次检查 |
| entry_owner | 持续调度、按rank处理、初始化、撤单、补单和进度投影 |
| entry_budget | 根据已核对的委托/成交与预占计算保守已用股数和金额 |
| EngineKernel | 账户、授权、实际预占、J1、报撤单和恢复的唯一所有者 |
| engine_daily | 读取冻结快照，将已保存目标或跳过原因交给现有每日上传流程 |

EntryPolicy正文hash与version必须同时匹配已验签计划的entry策略引用，rulebook_version及全部标的集合也必须一致。策略包含参考价、合法价格范围、价位、最小股数、步长、单笔量、来源hash、费用预留和容量参数。当前组件处理最多15个标的的非空计划；正式规则/来源交付和持仓订阅并集管理由后续宿主接线实现。

## 2 一次性目标

首次满足已授权、可信账户、执行窗口和合格行情时，按以下口径确定目标：目标名义金额、计划单票余额、会话总余额、可用现金减费用预留取限制，再结合当前受保护卖一价格、max_qty和合法数量步长计算。单笔数量、盘口深度和参与量用于后续拆单；它们暂时不足时可以先保存目标并等待。

目标只确定一次。价格变化、行情重发、撤单和进程重建均沿用同一目标。无法满足最小合法数量、持仓槽位不足、剩余首次执行窗口不足时，分别保存SKIPPED_MIN_ORDER、POSITION_CAPACITY、MISSED_ENTRY_WINDOW及零目标。资金不因跳过而扩大其他分配的target_value。账户级最终预算在每笔子单前重新求交集，因此目标代表执行意图，而非保证全部成交。

SQLite沿用既有六表27字段。新增正文使用recovery_checkpoints，字段含义如下：

| EntryTarget字段 | 含义 |
| --- | --- |
| plan_hash、policy_hash | 已验签计划与已安装策略正文摘要 |
| account_id、trade_date | 所属账户、交易日 |
| allocation_id、symbol | 原计划分配及证券 |
| boot_id、decided_at | 首次决定的进程代际及时间 |
| arrival_price | 首次合格卖一报价；无报价的跳过决定为空 |
| target_quantity、reason | 固定目标股数及初始化/跳过原因 |

同日上下文键entry-context:<日期>保存计划与策略，分配键entry-target:<计划摘要>:<分配编号>保存目标。相同正文可读取恢复，冲突正文使策略暂停。每个非空上下文最多15个目标。当前建立owner后冻结当日上下文，换计划采用后续显式迁移流程，保留旧证据。

独立目标写入成功后才形成子单。J1的EntryBinding增加可选state_hash并引用该记录。新字段为空时序列化省略，dev45/dev47旧记录正文和摘要保持兼容。新记录由dev48及后续兼容版本读取；回退前保留Journal并检查应用载荷兼容性。

目标保存与每个子单J1是两次独立短提交。原有单写者、100ms忙锁等待、250ms应用等待继续适用。目标提交或J1失败、超时或跨权限代际时暂停新派发；迟到结果用于恢复核对。行情、60秒容量输入和日常策略循环使用内存。以上仍是明确的本地持久化依赖，目标盘尾延迟继续现场验证。

## 3 补单与预算

本ADR将ADR-R31-005的纯尝试股数限制细化为两种兼容路径：旧J1继续累计完整尝试股数；带state_hash且安装了Entry状态闸门的J1，按以下条件回收未成交部分。

1. 最新账户观测已完成订单、唯一成交、持仓及窗口一致性核验，相关事实已完成关键保存。
2. 原订单为终态，唯一成交股数与终态累计成交一致。
3. 引擎已解除该订单预占。
4. 新子单继续引用同一目标，使用新的client_order_id、当前boot与权限代际。

未满足条件的订单继续按完整尝试股数与最大金额占用。满足条件后计入“已成交股数 × 原限价 + 原整笔费用预留”，只回收未成交本金；价格改善和费用预留继续保守占用。费用最终值由正式账单另行核对。

示例：目标100股、限价10元、每单预留5元。首次100股成交40股后撤单，核对前仍占100股/1005元；核对后占40股/405元。补单60股需605元，两笔合计100股/1010元。新单同时受剩余现金、分配金额、会话总额、单笔限额及持仓数量约束。

上述恢复样例使用明确的Mock最小10股规则；若实际已验证规则规定最小100股，剩余60股形成零新增子单，最终保留部分完成结果。数量合法性始终优先于补足目标。

## 4 调度和行情边界

- 按计划rank确定调度顺序，同股一个活动或不明订单；账户活动单上限由策略设置，最高3个。现有引擎的标的槽位包含实际持仓和当日已尝试标的，拒单后继续保留这一保守占用。
- 每个分配最多4个子单，即首次加至多3次补单。次数来自J1，重启保留。
- 每个行情序号在当前boot最多归属一个子单。J1等待中收到同价新行情时，派发复核使用其最新容量，通过后把新序号也归属当前子单，后续子单等待下一序号，防止盘口容量重复使用。行情失效、价格变化或容量不足则停止该次派发并恢复核查。源时间和接收单调时钟均满足冻结时效参数（最大5000ms），且盘口状态、价差、涨跌幅范围、有效申报上界和追价限制均通过。
- 当前成交量控制采用保守“当日已尝试股数 + 候选股数 ≤ 最新经核验60秒成交量 × 参与率”。撤单和重启保留已尝试用量。它可能减少后续交易机会；精确滑动窗口用量归因作为单独优化项，需随J1补齐可恢复的时间证据再放宽。
- 当前普通调整间隔使用策略cancel_after_seconds（样例20秒）。价格/市场条件变化且到间隔后请求撤单；停止新增窗口到来时，即使缺少新行情，也可按原订单及有效本地授权请求撤单。10秒加速阶段继续单列。
- 撤单受当前授权、Journal、已知券商订单号和cancel_by约束。HALT/授权过期后的券商在途仍可能成交，现场处置和后续核对继续承担该风险。

## 5 日终、验证和当前范围

引擎日终快照携带已恢复且已保存的EntryTarget。零目标导出SKIPPED和原原因；有目标而无订单导出目标数量及CANCELLED；缺少新J1所引用的目标记录时保留ENTRY_TARGET_EVIDENCE_UNAVAILABLE。日终仍由Windows任务调用量化接口，业务历史在量化系统查询；HTTP八类数据契约保持原样。

新增--simulate-entry-owner验证100→成交40→撤单→关闭重建→补60。原--simulate-business-flow的D0步骤已使用Entry owner，继续与D1退出及每日回传贯通。模拟规则中的10股步长明确属于测试夹具。

本轮验证属于离线组件与业务组合。长期独立engine/agent宿主仍为MOCK、安装额度0；策略与正式行情接线、来源文件交付、同日Entry/Exit切换、精确容量归因、10秒加速和完整进程强杀矩阵继续开发。现场QMT及实盘授权另行验收。
