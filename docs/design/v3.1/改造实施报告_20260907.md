### 2.1 SQLite现在具体保存什么

| 表 | 保存内容 |
| --- | --- |
| store_meta | 库版本、库身份、账户绑定与创建时间 |
| action_targets | 策略动作的目标剩余数量及规则绑定，约束重复动作扩大目标 |
| submission_records | 每次NEW/CANCEL的唯一ID、内容hash、最小提交载荷、动作关联、提交状态和时间 |
| broker_facts | 用于恢复的券商事实片段及幂等键 |
| control_records | 本地控制授权与暂停等恢复证据 |
| recovery_checkpoints | 恢复核对检查点 |

计划正文和每日待传批次采用不可变文件；盘中行情窗口和预占采用内存状态。上述新版库承担最小关键提交与恢复职责。旧版大Journal仍由旧装配使用，后续切换完成后按调用清单清理。

### 4.1 存储与提交故障测试

本轮覆盖：忙锁、队列满、排队超时、迟到COMMIT、HALT竞态、SDK已接收后超时、重复提交、库归属与账户不匹配、动作目标扩大、恢复内容损坏、在线备份/恢复、长读事务阻滞检查点、SQLite逻辑容量耗尽，以及COMMIT前后进程退出。

容量耗尽用临时数据库的`max_page_count`产生真实`SQLITE_FULL`，保留本机磁盘可用空间。该测试发现“SQLite自动回滚后再次回滚掩盖原始错误”的问题，现已改为检查事务状态并保留原始异常。失败后邮箱进入不可用状态，后续提交被拒绝。

进程退出测试表明该故障场景下动作目标和提交记录同时存在或同时缺失；成功提交后恢复出的重复记录仅作证据。该结论属于进程崩溃测试，物理断电、控制器缓存与目标存储介质另做现场专项。

### 4.2 开发机J1延迟

最终代码在开发机隔离库执行200次“排队 → J1 → 回执”往返：P50 0.568ms、P95 0.789ms、P99 0.886ms、最大2.453ms，环境为Python 3.11.16、APSW 3.53.4.0、SQLite 3.53.4。详见`journal-latency.json`。

这是短时开发机测量。两完整交易日负载、WAL持续增长、慢设备、杀毒干预、系统资源压力及目标QMT机器存储仍需验证，R31-003保持进行中。

## 5 如何运行已交付的模拟闭环

本机已经建立独立的Python 3.11验证环境。进入自动交易项目后执行：

```powershell
.\.codex_tmp\r31-venv\Scripts\python.exe -m auto_trading_system.apps.trade_runtime --simulate .codex_tmp\r31-demo
```

每次运行生成全新`simulation-...`子目录，其中包含独立Journal、计划和日终文件、回执及`result.json`。结果应包含`real_trading_enabled=false`、`filled_quantity=50`、`cancelled_remaining_quantity=50`、`submission_records=2`、`restart_paused=true`及`daily_upload_status=SYNCED`。这些是受控Mock场景的断言，不代表券商已接受真实订单。

其他开发机按照README使用Python 3.11建立环境并安装锁定依赖。上述`.codex_tmp`目录为本机验证工具，正式安装目录和任务发布包由R31-018交付。
