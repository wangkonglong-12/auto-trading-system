## 2 SQLite与内存的实际职责

SQLite仍是最小关键提交与恢复Journal，由原单一Journal线程访问。J1确认后才能进入报单边界；恢复/收盘检查点保存恢复证据。新增分片复用`recovery_checkpoints`表，SQL仍为Schema 1、六表27字段。

报价、策略计算、连续峰值及运行状态使用内存。普通日志、Tick归档和业务历史展示的职责保持原方案。量化系统仍使用现有MySQL承接每日交易、账单和对账结果，Windows任务主动拉取计划并按日回传。

本轮将大检查点拆成多条小事务，根清单最后提交。写入中断留下的分片继续保留；只有根清单与全部分片校验通过才构成完整检查点。恢复成功之后仍需本次启动的恢复确认与新授权。

| 容量或时限 | 当前边界 |
| --- | --- |
| 历史加当日扫描 | 最多100,000条，每页最多200条 |
| 当日J1留存 | 最多2,048条 |
| 存续历史SELL目标 | 最多2,048个动作 |
| 开盘/收盘批次 | 最多2,048个 |
| 逻辑检查点 | 最多8MiB、256个分片 |
| 单条SQL证据正文 | 最多64KiB |
| 暂停态完整恢复 | 30秒总时限，分页请求保持5秒 |
| 报单J1应用等待、SQLite锁等待 | 分别保持250ms、100ms |

这些值是安全预算；达到预算或验证失败时保持暂停。历史读取仍需扫描全部已封存记录，耗时随历史增长，100,000条上限不代表已完成该规模的目标机性能验收。数据库文件增长仍由后续备份和代际轮换工作处理。

## 3 已验证的容量与故障案例

### 3.1 超过原历史上限的恢复

隔离样本包含3,200条合成历史记录和120条当日提交。120条当日记录经统一SDK提交边界取得Mock拒单事实，成交为零。两次重建均完整扫描3,320条记录，只保留120条当日J1供订单核对；恢复结果CLEAR，权限保持暂停，历史删除数为0。

恢复证据正文为97,823字节，超过原单行限制，经3个分片完整保存并验证摘要。该样本验证容量、存储和恢复流程；合成历史封存仅用于测试，不代表真实金融对账资格。CLI每次新建独立目录，已有样本数据库拒绝重复初始化。

### 3.2 跨日与卖出目标

- 2,200条历史加4条当日记录完成恢复及收盘封存，摘要与独立读取全部2,204条的结果一致，原记录全部保留。
- 1,000个仍有持仓的批次通过分片开盘输入完整恢复，再次封存仍保留全部批次。
- D0买入100股、D1全部卖出后，新开盘载荷只保留实际存续持仓；历史两条J1和旧证据保留。
- 存续批次的历史SELL最紧目标继续约束新单，目标放宽和规则替换被拒绝。

### 3.3 中断、损坏和急停

故障用例覆盖缺片、无效Base64、分片/总摘要错误、错误长度和片数、非规范JSON、错误版本、行损坏、根键冲突及超限。

对首片、中间片及根清单写入分别注入故障，确认根清单未发布时不会暴露半份有效检查点，同内容重试可以完成。另启动专属存储写入子进程，在首片或根清单提交后实际强制终止，再重新打开数据库核验：首片阶段根不存在，根发布阶段正文完整。终止范围仅为测试创建的子进程。

引擎用例验证根清单完成前无法确认恢复；HALT、超时或磁盘失败后，迟到写入结果不能重新应用或提高权限。这里完成的是存储子进程强杀与引擎注入测试，完整engine跨进程强杀矩阵仍在后续计划中。

## 4 兼容、文件与生产边界

小正文继续使用原键和原格式；历史前缀摘要保持兼容。大检查点引入应用层`critical-blob-v1`格式，使用dev44及以后兼容读取版本。SQL结构版本相同不等于旧程序可以读取新分片格式；回退在暂停态保留完整数据库及版本，先验证读取能力。

本轮实现、测试、文档和证据均写入`E:/workspace/auto-trading-system`。量化项目仅进行文件摘要读取，本轮未写入或删除其文件，也未操作生产数据库、配置、任务或QMT。

量化目录同期存在外部变化：相对本轮872文件基线，快照时新增6个研究脚本/分析文档，修改`docs/CODEX_CONTEXT.md`，删除0。准确路径见`quant-boundary.json`。这些差异全部保留，并与本轮自动交易交付区分记录；不能将其描述为整个量化目录零变化。

本轮保留原Journal的历史订单、控制、回报、检查点和孤立分片。新封存中省略零持仓批次只改变下一日有效载荷，不删除原始数据。
