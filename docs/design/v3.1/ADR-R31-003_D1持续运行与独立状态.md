# ADR-R31-003 D1持续运行、独立规则状态与开盘上下文

日期：2026-09-21。状态：离线实现采用，正式来源适配及现场准入继续按R31验收。

## 1 决策与适用范围

D1退出使用独立、已验签的`ExitSessionContext`，引擎在同一owner线程内驱动退出策略。开盘持仓继续使用ADR-R31-002定义的同账户Journal封存及历史前缀验证。交易权限使用本次boot的恢复确认和本地SELL授权；策略上下文签名提供来源证明，授权提供执行许可，两者分别验证。

当前交付为固定Mock的离线组合根。正式签发方、Windows开盘任务、文件保护和进程间认证接线在R31-009/015交付；规则与来源事实适配在007/012/014交付。

## 2 职责和执行顺序

| 组件 | 当前职责 |
| --- | --- |
| `ExitSessionContext` | 冻结账户、策略、日期、开盘检查点、日历、批次、成本/前收/开盘价、价格档位/边界、数量步长、零股清仓规则、单笔限额及时间窗 |
| `ExitStateGate` | 同owner访问，保存最多15标的最新行情；按双时钟2秒新鲜度、连续交易窗口、价格约束和最新持久状态核验候选子单 |
| `D1StrategyOwner` | 每轮推进engine、处理异步状态结果、校验J1状态引用、计算规则和目标、处理到期撤单、形成受限子单 |
| `EngineKernel` | 管理恢复、授权、账户观测、订单、实际批次及预占；独立校验本地限额、T+1、目标、可卖量、数量步长和零股全量清仓 |
| `CriticalJournalOwner` | 使用既有SQLite/WAL单写者保存关键记录，并异步返回提交结果 |
| SDK工作线程 | 串行查询和报撤单；策略线程保持非阻塞 |

本地处理顺序为：已核对持仓和行情→纯规则评估→离散规则状态持久化→最新证据和权限复核→原J1提交→SDK派发。没有形成子单时，规则状态仍独立保存。已有委托在途时，收紧后的目标先保存；新子单等待原委托终态及成交、账户核对完成。

## 3 开盘上下文和权限

上下文正文采用规范JSON、SHA-256摘要及域分离Ed25519签名。签名域为`AUTO-TRADING/EXIT-CONTEXT/V1`。本地组合根提供已信任公钥，验证正文、签名、签发时间和有效期；engine再核验账户、日期、开盘摘要及完整日历摘要。

上下文最多15个批次，每个批次保存成本和行情规则来源摘要。价格档位、涨跌价格边界、卖出步长和零股规则均为显式输入，正式输入由合格来源适配器产生。本轮Mock使用可追溯测试常量，其中数量步长1只是测试规则。

SELL会话的买入额度固定为0，方向限SELL。计划摘要字段`plan_hash`继续作为兼容字段；`context_type=EXIT_SESSION`明确其引用退出上下文。下午Entry会话继续使用`ENTRY_PLAN`。当前boot选定一种执行上下文；同日退出与尾盘买入的会话切换交给后续受控切换流程验收。

同一账户、同一天的上下文正文在`recovery_checkpoints`中使用唯一键`exit-context:<date>`固定。相同内容重复加载可恢复；变化内容产生冲突并暂停。这样，重新签发上下文或更换编号也需要显式迁移与核对，而不会重置一次性检查。

## 4 独立恢复记录

SQL维持Schema 1、六表27字段。本轮在既有`recovery_checkpoints`中保存带字段说明的`ExitTransition` JSON：

| 字段组 | 含义 |
| --- | --- |
| revision / previous_hash | 会话内连续序号、上一条状态摘要 |
| context_hash / account_id / trade_date / lot_id | 冻结来源和批次归属 |
| boot_id / observed_at | 本次产生状态的进程代际和评估时间 |
| target_remaining | 原始批次最终目标剩余股数，只向小值收紧 |
| fired_rules | 已触发规则及已完成检查标记，只追加 |
| profit_armed / path_uncertain | 离散路径质量状态，恢复时保持保守约束 |

每个上下文最多256条状态记录。恢复读取所有256个有界槽位，检查序号、链接摘要、归属及单调性。达到容量上限进入暂停并要求维护核对。每条新SELL的`SellBinding.state_hash`绑定已提交的状态正文；恢复逐条验证J1引用存在，已有子单可以引用较早的合法状态，新子单必须引用当前最新状态。

行情价格、峰值及本进程单调时钟留在内存。只有离散规则/目标/质量变化触发状态写入。子单仍有原有的一次J1；当本次评估产生新状态时，前面另有一次关键状态提交。两步均是明确的存储依赖：状态或J1失败，新的自动买卖保持暂停。原100ms锁等待和250ms应用提交等待继续有效；超时后迟到提交只作为恢复事实。

## 5 连续处理规则

- 已完成的10:30、11:00检查，无论是否减仓，都保存检查标记。重启保留这些标记和目标。
- 新报价以标的为键覆盖最新值；未知标的拒绝，倒序序号、倒退单调时钟和未来时间触发暂停。
- 新子单使用UTC+08:00行情、双时钟2秒新鲜度及09:30—11:30、13:00—14:55:30时窗，并受签名上下文的更紧窗口约束。
- 数量受批次剩余减目标、预占、券商可卖、签名单笔数量/金额及本地限额共同限制；普通数量向步长取整，零股清仓要求本次数量等于批次全部实际剩余。
- 在途委托持续无更新达到签名参数`cancel_after_seconds`（样例30秒），或进入停止新增窗口时，请求撤单。撤单依据已知订单事实，可在行情过期时继续；本地授权、J1、急停和撤单截止时间继续生效。
- 重启保留目标和已检查状态，路径从不完整开始。当前保守owner执行开盘减仓、直接止盈、定时/成本及最终退出规则；峰值回撤条件等待Recorder/Replay提供完整路径后接入。

## 6 兼容、业务归宿与后续

旧BUY/SELL正文的新增默认字段在序列化时省略，原J1摘要和幂等含义保留。`EXIT_SESSION`记录由dev43及以后兼容版本读取；回退采用停机、数据保全及兼容读取验收。

日终记录、账单、对账与历史页面仍由Windows定时回传至量化系统现有MySQL。退出状态与批次级审计的中央导出契约、来源覆盖及页面继续由002/010/011/016实现。本轮只导出本地Schema，量化后台、共享HTTP结构及生产数据库维持原状。

长期容量、完整路径回放、会话切换、受保护开盘任务和真实QMT分别验收。当前R31工作包保持IN_PROGRESS/PENDING/NOT_READY；本次离线闭环作为其中一项可复现证据。
