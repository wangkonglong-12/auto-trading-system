已实现并验证计划/日终V2 HTTP链路：量化读取正式来源、冻结预算和来源、发布签名计划；Windows主动获取、验签、加载回执；八类日终记录分片上传、原子切换日版本、保存回执，以及服务端恢复旧数据后的重新补传。

## 2 已实现内容

### 2.1 契约与校验（R31-002）

- `contracts/v2`输出16份Schema、9个已实现节点接口的OpenAPI 3.1和公共签名测试向量；两项目8个共享协议源文件有一致性回归。
- 八类日终记录：计划结果、关键提交、券商委托、券商成交、持仓、资产、对账、事件。金额采用十进制定点字符串，数量采用整数；校验账户、日期、订单数量关系、成交所属交易日、观测截止点和对账一致性。
- 本地控制请求/结果、会话授权的载荷已定义，包括账户、节点代际、engine启动标识、绝对限额、有效窗口与恢复证据。动作契约已交付；全部动作的正式执行与持久化装配仍待完成。
- HTTPS校验证书链和主机名，禁止重定向；请求与响应均验签、限制字节数，重试保持业务ID和正文不变。HMAC防重放nonce通过MySQL唯一约束原子占用，4并发同nonce测试只有一个成功。
- Ed25519计划签名与节点上传HMAC分别配置。实际发布器拒绝公共测试种子；测试向量中的密钥仅供复现测试。

### 2.2 正式来源与计划发布（R31-008）

新增独立模块读取`tail_hot_pick_runs`与`tail_hot_picks`：只选择当日14:40、正式角色、定时来源。读取使用短只读一致性事务；最新正式运行未完成时返回未就绪，最新正式结果为空时保持空计划。旧来源首次模块快照记为revision 1，同版本内容变化判为冲突。

账户预算使用显式批准的绝对金额、证券数上限、单证券上限、策略版本和执行窗口。批准与来源分别保存不可变快照；按排名选取、按分向下分配，剩余金额保留为现金。计划业务键绑定账户、策略、日期、来源版本及预算版本；重复发布返回同一计划，已撤回计划保持撤回状态。

接口注册沿用现有自动交易子模块入口；`AUTO_TRADE_MODULE_ENABLED`与`AUTO_TRADE_V2_ENABLED`共同控制路由。发布器另需`AUTO_TRADE_V2_PLAN_PUBLISHER_ENABLED`。三个开关默认均为false。V1与V2发布器同时启用会报配置冲突。

**现有正式来源的具体接入缺口：** 旧来源尚未提供`market_coverage_bps`及`market_coverage_basis`。发布器返回`SOURCE_COVERAGE_UNAVAILABLE`或`SOURCE_COVERAGE_BASIS_MISSING`，保持计划未就绪。后续需在专属适配层接入可追溯的全市场覆盖分母、有效数量和时点证据；该项属于待开发的接口适配，不能拿入选数量、候选覆盖率或`data_health=full`替代。旧来源也没有独立发布时点：适配器目前用成功完成时点表示其正式可读时点，量化签名计划实际持久化时间另存于计划表。

### 2.3 Windows主动同步组件（R31-009/010）

`AgentJobs`负责计划拉取、加载回执和日终续传。它持有账户/节点级Windows互斥锁，在14:20—14:55的交易日窗口拉取计划。不可变正文使用内容hash命名；任务索引使用独立小文件、校验和及原子替换，默认上限4,000项，单次重试最多64项。任务不会写入最小SQLite Journal，也不会调用券商报单。

`EnginePlanControl`在engine所有者线程独立验签并核对账户、日期、策略、代际、规则版本。加载计划与授权交易是两个步骤；未授权撤回清除候选，已授权计划变化触发暂停并保留冻结计划。权限收紧失败上抛engine故障，产生成功回执之前必须确认动作完成。当前该端口在集成测试中为进程内调用，本机命名管道/ACL接线仍待完成。

新增正式导出映射，固定Mock模拟入口也使用八类金融记录校验。日终清单明确每类数据是完整零笔还是缺失；分片最多200条/512KiB，批次最多16MiB。服务器APPLIED回执通过身份和签名校验后才标记同步完成。

任务重试保留原文件和业务ID；更正版本先检查前序版本，服务端恢复旧点后先补旧版再补更正版。本地任务结果写失败直接报告存储故障，保留原状态供再次核验，避免误记同步成功。

### 2.4 量化接收、隔离与数据库升级（R31-011/018）

量化沿用现有MySQL。V2连接使用独立的两连接限额和短事务，HTTP处理使用独立两工作线程；超额请求返回忙状态。集成测试覆盖两工作线程占满时普通量化测试路由仍可响应。程序停止时释放本模块线程，并保留原应用生命周期。

日终分片与记录先准备，最终短事务同时更新账户交易日可见版本指针和APPLIED回执。完整性与财务结算状态分开：当前财务状态为`PROVISIONAL`，真实费用/账单到齐后的`SETTLED`尚未实现。

新增显式迁移工具`backend/scripts/auto_trading/migrate_v2.py`。默认只打印离线计划，不连接数据库；读取校验和实际应用均要求明确数据库名。迁移只处理固定清单中的12张`auto_trade_`表：日终5张、计划/绑定/回执4张、来源/批准2张、专属迁移登记1张。71个字段全部具有数据库注释。

升级前核对所有已有目标表的字段类型、可空性、默认值、注释、字符排序、主键、索引、外键与触发器；发现冲突即停止。迁移登记文件字节hash；既有登记与文件不一致时拒绝执行。MySQL DDL隐式提交，失败后保留已创建对象，经检查续跑；已登记表丢失要求恢复，工具不会将其自动重建为空表。

已有V1治理表由原安装流程提供；新版工具检查前置字段而不改造这些表。正式部署的备份、版本兼容、回退与目标库性能验收仍属于R31-018/019。

## 3 已实现的9个节点接口

统一前缀：`/api/v2/trading`。

| 方法与路径 | 用途 |
| --- | --- |
| GET `/manifest` | 协议能力、限额、受信计划密钥标识 |
| GET `/plans/current` | 当前计划/显式撤回状态，支持ETag |
| GET `/plans/{plan_id}` | 读取固定不可变签名计划 |
| POST `/plans/{plan_id}/receipts` | 上传engine加载/拒绝/暂停回执 |
| POST `/daily-syncs` | 登记不可变日终清单 |
| PUT `/daily-syncs/{batch_id}/parts/{part_id}` | 幂等上传分片 |
| GET `/daily-syncs/{batch_id}` | 查询批次状态与缺失分片 |
| POST `/daily-syncs/{batch_id}/complete` | 完整性校验与原子应用 |
| GET `/daily-syncs/{batch_id}/receipt` | 查询持久化最终回执 |

账单上传/结算接口和管理端历史查询接口另行交付，不包含在这9个接口的完成声明中。

## 5 边界与当前限制

1. SQLite继续承担最小提交/恢复Journal；盘中Tick与策略计算使用内存。本轮HTTP同步、任务索引和中央日版本均未扩大SQLite职责。
2. 历史交易、中央日版本、账单、对账结果最终在量化系统查看；Windows负责主动拉取与日终回传，现场台承载本机操作状态。
3. 客户端连接预算3秒，普通请求/分片分别配置8/15秒I/O超时并检查累计耗时；这不是强制终止底层调用的精确墙钟承诺。服务端7.5秒协作预算阻止继续发起SQL，单次驱动调用仍由驱动超时约束。端到端严格时间上界与长时压力还需专项验收。
4. nonce的过期判定与原子再占用已实现；过期记录的有界维护清理任务尚待完成。任务/文件保留与归档策略也待正式维护装配，当前达到容量上限会明确停止接收新任务。
5. 旧V1模块、页面、探针和启动装配仍有调用者，继续保留；新版完整接线后逐文件清理失去调用者的代码。没有删除量化后台原有业务文件。
