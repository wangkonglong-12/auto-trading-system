# V3.1 独立进程、认证通信与Windows任务实施报告

日期：2026-09-23。程序版本：0.1.0.dev46。Windows开发环境：Python 3.11.16、pywin32 311。

## 1 交付结论与运行边界

本版交付可独立启动的engine、agent和薄JobRunner，将已有计划、日终、任务索引及新版引擎组件接入真实Windows命名管道。任务定义可生成、由Windows调度器解析校验，并通过显式部署命令注册。

当前开放的进程配置为MOCK：能够启动恢复、接收签名计划、保持暂停、盘后生成日终文件、由独立代理上传和恢复补传。订单额度为0，交易提交接口保持关闭。既有两天买卖验收仍使用dev45专用模拟入口。本次运行基础设施通过不等于正式策略全天运行或真实QMT交易已验收。

历史开发顺序先做了交易/恢复内核和同步组件，进程接线滞后。旧任务脚本确实存在，面向旧装配；本版增加具备独立名称和明确入口的V2任务，保留旧版本与现场证据。

## 2 实际进程与调用链

| 单元 | 入口 | 拥有的资源及实际职责 |
| --- | --- | --- |
| engine | `auto-trading-node --config PATH engine` | 账户互斥、单owner引擎、Journal线程、SDK线程；加载计划、恢复、状态、日终快照及后台文件冻结 |
| agent | `auto-trading-node --config PATH agent` | 独立进程、单作业线程、HTTPS客户端、文件作业索引；拉取、上传、回执补查和启动补传 |
| JobRunner | `auto-trading-node --config PATH job KIND` | 向agent发起一次作业，等待对应调用结果并返回退出码；QMT会话与关键数据库由engine持有 |
| 现场CLI | `status engine/agent`、`halt`、`stop engine/agent` | 使用operator凭证查询、锁存急停及正常退出 |

计划链：Windows任务 → JobRunner → agent管道 → HTTPS拉取及验签 → 不可变计划/lookup文件 → engine管道 → owner加载 → 加载回执 → 量化系统。

盘后链：15:30任务 → agent请求收盘重新核对 → 等待该次核对的状态版本 → owner冻结快照 → engine管道工作线程打包八类文件 → 发布日期引用 → agent登记文件作业 → HTTP分片上传 → APPLIED回执。

日终冻结线程只接收不可变快照，owner继续处理循环。operator控制管道与同步管道分开。状态由owner每100ms发布带时间戳的只读副本，查询状态不等待owner，避免查询占用急停通道。页面、网络、日终文件均不成为交易权限来源。

## 3 本机通信与权限

- 传输：本机Windows Named Pipe、pywin32、4字节大端长度+UTF-8 JSON、最大64KiB。计划和日终正文走受保护的内容寻址文件，管道只传固定摘要。
- 命名：节点/账户摘要决定engine、control和agent管道名；首实例句柄在进程寿命内保留，重复绑定失败；管道拒绝远程客户端。
- 身份：显式DACL仅放行配置的运行用户与SYSTEM；连接后核对客户端用户SID。进程也核对自身SID与配置一致。
- 应用认证：agent、jobrunner、operator使用三份独立HMAC凭证，量化HTTPS使用第四份；凭证按引用从Windows凭据管理器读取。环境变量引用仅用于隔离开发测试。
- 消息：协议主版本、请求ID、目标启动ID、角色、截止时间和动作参数一起签名；回执签名绑定原请求摘要。HELLO取得本次启动身份，旧启动请求失效。
- 权限：agent可加载计划、请求收盘核对/导出和读状态；jobrunner可触发规定作业和读状态；operator可读状态、HALT及STOP。交易授权和报撤单继续由独立受控流程接线。
- 重试：单管道512项短期结果缓存，相同请求ID和正文返回原结果，冲突正文拒绝。进程重建后使用新的启动ID；业务幂等依据计划回执、文件摘要和持久作业身份。

同一Windows用户内运行的程序属于同一操作系统信任边界；角色密钥减少误调用和混用，不表示可抵抗已控制该用户的恶意程序。部署时使用专用用户并保护配置、安装包和凭据。后续supervisor继续负责进程路径/创建时刻及安装摘要核验。

| 预算 | 本版实施值 |
| --- | --- |
| 控制帧 | 64KiB |
| 已连接客户端读取请求 | 2秒 |
| 单管道连接处理 | 7秒，重叠I/O超时后取消并回收缓冲 |
| 请求有效期 | 最大8秒；客户端默认7.5秒 |
| owner交接 | 队列8项；最多4秒且受原请求剩余时间限制；领取前超时取消 |
| 同步作业并发 | agent单作业；JobStore另有账户/节点OS互斥 |
| HTTPS作业 | 每次作业90秒准入预算；已开始单次请求按原8/15秒预算完成，后续请求保留到重试 |
| JobRunner等待 | 480秒；结果不确定返回失败，由下一任务重试 |
| 日终发现 | 3660个日期引用上限；逐个读取完整清单，历史清单不一起留存内存 |

超时只限制本次等待和后续准入，不能撤销已经执行的动作。HALT先锁存权限，STOP先锁存再退出；已接受的STOP连接完成回执传送后关闭，防止正常退出丢失答复。

## 4 文件与恢复

`data_root`专属目录包含`node-scope.json`、`critical`、`artifacts`、`daily-catalog`、`jobs`、`logs`。初始化显式创建全新目录并设置用户/SYSTEM继承ACL；已存在目录拒绝初始化，保留其文件和权限。启动逐一检查目录ACL、链接以及节点/账户/部署与Journal代际标记。

日终文件写入、刷新及校验完成后，以同卷不可变链接发布`daily-catalog/YYYY-MM-DD.json`。代理在每次日终/补传及启动补传时发现引用。因而“文件已冻结、代理尚未登记作业”期间被结束的代理，重启仍可找到批次；已登记作业继续沿用原批次和日期。今天重试复用已发布批次；更正版引用替换列为后续显式流程，不能由重复任务悄悄覆盖。

代理被结束只影响同步，引擎保持原启动身份和暂停/交易状态。引擎重启创建新boot，恢复时保持暂停，旧授权失效。启动时尚无计划但账户确实为空，可以完成空账户核对；有J1、开盘持仓、委托或成交时仍需明确归属证据。进程跨自然日退出并锁存暂停，次日08:40任务启动新交易日实例；跨日开盘引用和正式策略来源装配继续单独推进。

SQL六表27字段保持原样，本轮新增状态和配置字段均在独立类型/Schema中定义。pywin32进入两份带hash依赖锁；原量化后台依赖保持原样。

## 5 Windows任务定义

| 任务后缀 | 触发 | 命令行为 |
| --- | --- | --- |
| Engine | 专用用户登录、工作日08:40 | 启动engine，运行时忽略新实例 |
| Agent | 专用用户登录、工作日08:40:10 | 启动agent，并执行启动补传 |
| PullPlan | 工作日14:20起每分钟，覆盖至14:55 | `job pull-plan`；程序再核对交易日和时间窗 |
| DailyExport | 工作日15:30 | `job daily-export`；核对、导出及上传 |
| DailyRetry | 工作日15:45起每15分钟，覆盖至18:00 | 同一日终命令；首次失败时也会补做导出 |
| CatchUp | 工作日08:45 | `job catch-up`；按原批次日期补传/补查 |

名称为`AutoTrading.V2.<节点账户摘要>.<后缀>`。任务使用指定用户的交互登录会话、普通权限、IgnoreNew和过期触发补跑；engine/agent失败按1分钟间隔重试最多3次。任务触发只是唤醒，业务交易日和窗口由程序再次判定。专用用户未登录时的全天无人值守、会话断连和目标机重启行为属于现场部署验收。

安装脚本默认生成并校验计划。显式`-Apply`才注册；预先检查六个目标都不存在，避免覆盖既有任务；部分注册失败只回滚本次成功创建的精确任务名。旧V1任务脚本、其他Windows任务和已有配置全部保留。停止/迁移旧版本由部署清单确认，不能同时把两套引擎作为有效交易节点运行。

## 6 配置与操作

示例：`config/v2/node.mock.example.json`。Schema：`config/v2/node-config.schema.json`。示例SID、公钥、日历、策略hash、账户和地址属于说明样本，正式使用前替换为当前节点值，并为凭据引用配置不同的随机密钥。

现有凭据工具增加`--kind ipc-hmac`；交互输入密钥，命令行只包含目标引用。HTTP密钥继续使用`--kind node-hmac`。任务参数及计划输出均不携带密钥正文。

以下命令以已安装的`auto-trading-node`及用户自备配置为例：

```powershell
auto-trading-node --config C:\AutoTrading\config\node.json init
auto-trading-node --config C:\AutoTrading\config\node.json check
auto-trading-node --config C:\AutoTrading\config\node.json engine
# 在另一个终端运行代理：
auto-trading-node --config C:\AutoTrading\config\node.json agent
auto-trading-node --config C:\AutoTrading\config\node.json status engine
auto-trading-node --config C:\AutoTrading\config\node.json job catch-up
auto-trading-node --config C:\AutoTrading\config\node.json halt
auto-trading-node --config C:\AutoTrading\config\node.json stop agent
auto-trading-node --config C:\AutoTrading\config\node.json stop engine
```

`init`的父目录需事先存在，目标数据目录应为全新专属目录；`check`验证配置与目录权限/归属，具体凭据读取在相应进程/任务启动时检查。日历之外和窗口之外的计划/日终触发返回SKIPPED。JobRunner只有SYNCED或SKIPPED返回0，待补传/人工处理返回1，入口或通信失败返回2。状态成功表示该查询有答复，不表示已取得交易授权。

任务脚本：`scripts/windows/install-node-tasks.ps1 -Python <绝对python.exe路径> -ConfigPath <绝对配置路径>`。审核计划后使用同脚本加`-Apply`进入注册确认。脚本会通过Windows Task Scheduler COM接口解析六份XML，但默认不保存任何任务。
